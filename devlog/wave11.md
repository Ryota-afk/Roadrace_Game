## 調査で分かったこと

### 発見1（最重要）：シーズンの順位表は張りぼてだった

`domain/season/standings.js` の `computeStandings(g)` は、他チームのポイントを
**チーム名のハッシュから作った固定の強さ × 月進捗**で生成しているだけ。
状態を持たず、レース結果を一切参照しない。

実測（`scratchpad/standings_check.mjs`）：

| 自分のポイント | 他チームの順位表 |
|---|---|
| 0pt | レッドサンダー山陽:43 / ヴェロチタ京都:42 / … |
| 500pt | 同上（**1ptも動かない**） |
| 5000pt | 同上（**1ptも動かない**） |

月推移も 1月:6 → 4月:24 → 7月:43 → 10月:61 → 12月:73 と**完全な直線**。

**「リーグ全体の流れが把握できない」のではなく、シーズンには流れが存在しない。**
画面の文言「他チームも毎月ポイントを積み上げています」は実態と食い違っている。

### 発見2：マイライフには既に本物の土台がある

- `riderStats`（`state.js`・マイライフのみ）＝全出走AI選手の実成績台帳
  （kind: world / rival / teammate / protege、通算＋年別の races/wins/podiums/bestRank）
- `mlWorldRaceLite(ml, seed)`＝**自分が出走しなかった月のレースも裏で決着**させ、台帳に積む
- `mlWorldTeamStats(ml)` / `mlRiderStatsRows(ml)`＝チーム別・個人別の表示用整形（純関数）

つまりマイライフは#25が求める「誰が強いか・誰が伸びているか」に答えるデータを既に持っている。
**シーズンには`riderStats`の受け皿（`initGame`の`riderStats: {}`）だけがあり、一度も書かれない。**

### 発見3：マイライフの「二重世界」

同じ「世界」を指す集団が2つ並存している：

| | 実体 | 役割 |
|---|---|---|
| `worldRosters` | 8名 × 9チーム＝**72名**・永続・`ageWorldRosters`で加齢/引退/補充 | **実際にレースへ出てくる相手** |
| `mlWorldStarsForYear` | **24名**・`ml.worldSeed`から毎回1年目より再シミュレート | 世界ランキング表示用。殿堂の血の流入先 |

ランキング上位の選手は、実際のレースにはグレードに応じて時々AIチームのエース枠を
差し替える形でしか現れない（`worldStarTeams`）。だから「世界1位」と「いつも自分と
走っている強い相手」が噛み合わない。

### 発見4：#24（能力開示）の現状

- `domain/shared/forecast.js` の `raceForecast()`＝出走表の予想印（◎本命/○対抗/▲注目）。
  コース適性順に**上位5名だけ**印がつく。両モード共通の純関数。
- シーズンの自チーム一覧は `overall(r)` でOVR表示。
- **相手選手の個別能力を見る手段は無い。**

### Phase 1：シーズンの順位表を実体化する（2026-08に大幅拡張）

当初は「`g.rivalPoints`を作って`computeStandings`が読む」だけの小さな話だったが、
25チーム化（人口拡張）後の再設計とユーザーとの対話で、**「リーグが実際に回る」**という
より大きな単位に育った。経緯と最終設計を以下に記す。

#### 発端1：25チーム化の副作用（未報告だった回帰）

`buildMyLifeSim`は`MYLIFE_TEAMS.forEach`で**全チームを毎レース出走させる**作りだったため、
チーム数9→25の拡張がそのまま出走人数に乗っていた。

| | 拡張前(9チーム) | 25チーム化後 |
|---|---|---|
| 出走人数 | 約34名 | **93〜101名** |
| sim処理時間 | 約150ms相当 | **460〜690ms** |

ポイントは`PTS = [10,7,5,3,3,1,1,1,1,1]`で上位10位までしか入らないため、100人レースでは
入賞難易度が実質3倍になっていた。実測は`scratchpad/field_size.mjs`／`field_size2.mjs`。

#### 発端2：順位表がクラスと無関係だった

`computeStandings()`は`RIVAL_TEAMS`（6チーム）を、プレイヤーがB1でもPROでも一律に並べていた。
かつ`RIVAL_TEAMS`のtier内訳は0/1/2が各2チームずつで、**クラス別に割ると各2チームしか残らない**。
＝クラス分割を成立させるには、Season側を25チームの世界へ載せ替えるのが前提になる。

#### ユーザーの設計方針（2026-08・この弾の中核）

> 「自分がでなかったレースを裏で決着させる仕組みはあってもいい気がする。今後レース数を
> 増やしていくことも考えていて、そうなるとチームによっては競合ばかり出てくる星数が多い
> レースを避けて星1のレースで表彰台独占を狙ってポイントを稼ぐみたいなことができても
> 面白いと思うんだよね。だから、一つのレースに全チームが集結するみたいな形はあんまりかも。」

**＝AIチームの「出走するレースの選択」自体をゲームの駆け引きにする。**
当初案（同クラスの全チームが毎レース集結し、裏レース決着は不要）は明確に却下された。

#### レース構造の調査結果

- **Season**：月5戦生成、うち自クラスに開かれるのは2〜3戦、プレイヤーは**月1戦だけ出場**
  （画面にも「出場は月1回」と明記済み）。残りは他クラス限定として既にグレーアウト表示されている。
- **MyLife**：`mlGenRace`が返すのは**月1戦のみ**。プレイヤーは出るか出ないかの二択。
- `buildSim`はカレンダーのクリック時点で相手チームの布陣を生成し`pendingAiTeams`へキャッシュ
  している（出走表と本番の顔ぶれを一致させるため）。**ここが出走登録の差し込み口**になる。

#### 確定した設計

**1-A：クラス分割（25チームのtierをそのままクラスとする）**

tier内訳は既に B1=9 / A=8 / PRO=8 とほぼ均等。両モードとも**プレイヤーの現在クラスの
チームだけ**を相手にする。`data/teams.js`に`teamsForClass(classIdx)`を新設。

- Season：`RIVAL_TEAMS`(6)→ 25チームをクラスで絞った8〜9チームへ。`rivalRosters`・
  `ageWorldRosters`・`genPoachTargets`の参照先も25チーム側へ寄せる。
- MyLife：`MYLIFE_TEAMS.forEach`→ 自クラスのチームのみ。出走が約34名に戻り回帰が解消する。
- **注意（実装時の落とし穴）**：MyLifeは`classIdx`がポイントで昇降格し、**所属チームのtierとは
  独立に動く**（tier0のチームに居たままクラスAへ昇格し得る）。対戦相手リストは
  `teamsForClass(classIdx) ∪ {自分の所属チーム}`にすること。
- `createChar.js`の初期所属チーム抽選は現在`tier <= 1`だが、開始クラスは常に0なので
  `tier === 0`へ揃える（既存の不整合の是正）。
- 旧セーブの`rivalRosters`は6チーム分しかないため、読み込み時に`topUpWorldRosters()`で
  欠けた19チームを補う移行を明示的に通すこと（同関数は`next[d.name] || []`から埋めるため
  チームごと欠落していても動く）。

**1-B：出走登録 `raceEntryPlan()`（Season専用・新規純関数）**

新ファイル `src/domain/season/entryPlan.js`（JSXを含まない＝Node単体テスト可能）。

```
raceEntryPlan(races, teams, rosters, year, month) → { [raceId]: [teamName, ...] }
```

**アルゴリズム＝強いチームから順に選ぶ逐次選択（混雑モデル）**：

1. その月の自クラス開催レースを列挙する
2. 各チームの地力（ロースター上位のbaseline合計）を出し、**強い順に並べる**
3. 強いチームから順に、各候補レースを評価する
   - `グレード倍率（GRADE_MUL）× 脚質適性（team.spec と tmpl.favors の一致で加点）
     ÷ 混雑度（既に登録済みチームの地力合計に応じて増える）`
4. 最良のレース1つに登録する（**AIも月1戦＝プレイヤーと対称**）

強豪が★★★に集まった時点で、後から選ぶ弱小チームには「★1が空いている」と見えるので
そちらへ流れる。**＝ユーザーが望んだ「競合を避けて★1で稼ぐ」がヒューリスティックの
副産物として自然に出る**（明示的にルールを書き込むのではなく、混雑の結果として創発させる）。

- **決定論的であること（必須）**：`year`・`month`からシードする。`Date.now()`は使わない。
  プレイヤーが選ぶ前に確定し、選んだ後も動かないことがこの遊びの前提になる。
- プレイヤーの自チームはこの計画に含めない（手動で選ぶため）。
- 8〜9チームが2〜3レースに分散するので、1レースあたり3〜4チーム＝**約17〜23名**の想定。

**1-C：裏レースの決着とポイント累積**

- `g.rivalPoints`（チーム名→累計pt）を新設、`SAVE_FIELDS`へ追加。
- **プレイヤーが出走したレース**：`sim.ranked`から各AIチームへ配分。
- **出走しなかったレース**：登録チームだけで軽量決着（`mlWorldRaceLite`と同じ
  「baseline＋地形適性＋ノイズでスコアリングして順位付け」方式のSeason版）してポイントを積む。
- 年度替わりで`rivalPoints`をリセットする（`g.points`と同じ扱い）。

**1-D：ポイント算定を「上位10位以内の全選手の合算」へ変更（ユーザー判断）**

現行は自チームも`PTS[best.rank - 1]`＝**最上位1人分だけ**。これを、そのチームの
上位10位以内に入った**全選手の合算**に変える（1位+3位なら 10+5=15pt）。

- 理由：ユーザーの言う「★1で表彰台独占して稼ぐ」が実際に成立するようにするため。
  ロースターの層の厚さと出走メンバー選びにも意味が生まれる。
- **既存仕様との整合という副次的な根拠**：賞金は既に
  `playerRs.reduce((s, e) => s + (PRIZES[e.rank-1] || 1), 0)` と**全選手合算**になっている。
  ポイントだけが最上位1人分という非対称だったので、合算化はむしろ整合を取る変更。
- AIチームも必ず同じ物差しで数える（片方だけ合算だと構造的な有利不利が生まれる）。
- **要較正（必須）**：全体のポイント額が1.5〜2倍になるため、`CLASSES`の`need`
  （45/50/60）は実測して引き直す。順位表は`seasonRank()`→`champPromoteCut()`経由で
  **昇格ボーダーに直結**するため、較正前後で昇格成功率を必ず実測比較すること。

**1-E：カレンダーUIに出走チームを見せる**

各レースにどのチームが登録しているかが**選ぶ前に見えないと、この遊びは成立しない**。
CLAUDE.md §7に従い、長い説明文ではなく**図・強弱で読ませる**こと
（例：登録チームのカラードットを並べ、混雑度が一目で分かる形にする）。
「出場は月1回」の既存文言との整合も確認する。

**MyLifeへの適用範囲（ユーザー判断）**：MyLifeは**1-Aのクラス分割だけ**適用する。
月1戦しか無く、プレイヤー側の戦略選択にならないため。自クラス8〜9チームがその月の
一戦に全員集まる形＝出走約34名で、キャリアモードとしての場の大きさも保てる。

#### スコープ外（今回やらないと決めたこと）

- **チーム自体の昇降格**（tierを可変にする）。実装が跳ね上がる割に「PROの強豪は常に強豪」
  という構図は自然なので、tierは固定のままとする。将来やりたくなったら別の弾で。
- プレイヤーが月2戦以上出場できるようにする改修（AIも月1戦にしたので対称性は保たれている）。

#### 検証計画（1-A〜1-Eの実装後に必ず実施）

1. **出走人数の実測**：Season約17〜23名／MyLife約34名に収まっているか。sim処理時間も併せて。
2. **ポイント分布の実測と`need`の再較正**：合算化で1.5〜2倍になる前提。昇格成功率を
   変更前後で比較する。
3. **出走登録の妥当性**：★3に強豪が集まり★1が空くという分布が実際に出ているか。
   同じ年月で必ず同じ計画になる（決定論）ことも確認。
4. 旧セーブ互換：`rivalPoints`不在／`rivalRosters`が6チームのセーブでクラッシュしないこと。
5. 両モードのPlaywright回帰＋`npm run build`。

**実装した項目（1-A〜1-E、設計どおり）**：

- 1-C：`g.entryPlan`（レースID→登録チーム名配列）／`g.rivalPoints`（チーム名→累計pt）を

- 1-E：`calendar.jsx`にカラードットの参戦表示（CLAUDE.md §7準拠、長文の代わりに

  「5チーム・激戦」等が正しく表示されることを確認。

### Phase 2：マイライフの世界ランキングを実際の対戦相手から作る

#### 着手前の実態調査（2026-08・Opusによる計測。設計の前提）

**① 「世界ランキング」は順位ではなく自分だけの計算式だった。**
`computeWorldRank(points, year)`は`ceil((P1/points)^(1/0.72))`で、**他人の成績を一切参照しない**。
実測：`worldPoints=600`なら1年目でも5年目でも無条件に「世界1位」（150ptなら1年目4位/5年目7位）。
＝順位ではなく、自分の持ち点を順位っぽいラベルに変換しているだけ。

**② 世界が3つに分裂している。**

| | 実体 | 人数 |
|---|---|---|
| 自分の順位 | 上の計算式 | 対戦相手なし |
| ランキング表の顔ぶれ | `mlWorldStarsForYear`（`worldSeed`から毎回1年目より再計算） | 24人 |
| 実際に走る相手 | `worldRosters`（永続・加齢/引退あり） | **300人** |

**③ Phase 1で新たな不整合が生まれていた（今回発見）。** `mlWorldRaceLite`は今も
`Object.entries(rosters)`で**全25チーム＝288人を1レースで決着**させる。一方Phase 1で実レース
（`buildMyLifeSim`）は自クラスのみ（9チーム≒36人）に絞った。結果、同じ`riderStats`台帳に
「288人中3位」と「36人中3位」が**同じ"表彰台1回"として混ざっている**。

**④ 世界スターは毎レース別人になっている（バグ）。** スターはAIチームのエース枠に差し替えて
実際に出走する（`state.js:917`の`worldStarTeams`）が、`newRider()`が採番する新しいidを毎回
振り直す（`id: ridState.value++`、rngは`mulberry(Date.now() % 999983)`）ため、台帳には
「1レースだけ走った幽霊」が毎回増え続け、スター自身の通算成績は永遠に積まれない。

**⑤ 土台は既にある。** `riderStats`は既に**全300人分**を`kind:"world"`として記録済み
（`races/wins/podiums/top10/bestRank/byYear`）。Phase 2は「台帳を作る」のではなく
**「既にある台帳を使って順位表を作る」**作業である。

#### 合意した設計（2026-08・`AskUserQuestion`で3点確認）

**2-A：台帳の母集団を揃える（前提条件）**
`mlWorldRaceLite`をクラス別に分割し、毎月**3クラス分を並行して決着**させる（自分が走った
クラスはその実レースの結果を使い、残り2クラスは軽量決着）。これで全選手の着順が同じ土俵
（1レース≒36〜40人）になり、③の不整合が解消する。

**2-B：台帳に世界ポイントを積む**
`riderStats`の各エントリに`wp`を追加し、全員が`worldPointsForFinish(着順, グレード) ×
クラス係数`で積む。年度末の減衰（×0.72、現在は自分にだけ掛かっている）も**全員に等しく適用**。
- **クラス係数＝1.0 / 2.0 / 3.5（B1/A/PRO）＝ユーザー判断**。シーズンの`CLASSES.prizeMul`と
  同じ値。「はっきり差をつける」＝PRO昇格の価値を大きくする方針。
- **要注意（2-Eで必ず実測）**：この係数だとB1・A時代は何をしても世界ランクがほぼ上がらず、
  序盤が死に指標になりやすい。特に**野望の`rankAtMost`条件（`state.js:546`）が
  キャリア序盤で達成不能になっていないか**を必ず確認すること。

**2-C：本物の順位に置換**
全台帳エントリ＋自分を`wp`でソートした実順位を返す純関数を新設し、`computeWorldRank`の
曲線を置換する。300人いるので`worldRankTier()`の300位スケールが初めて実体を持つ。

**2-D：`mlWorldStarsForYear`を完全に退役（ユーザー判断）**
24人の別世界を廃止し、実際に走る300人だけの1つの世界にする。担っていた4つの役割を移す：
1. ランキング表の顔ぶれ → 2-Cの実順位
2. 🩸殿堂の血の流入 → `worldRosters`の世代交代（`ageWorldRosters`/`topUpWorldRosters`）へ移植
3. 📰世界ニュース（`mlWorldNews`）→ 実順位の年次変動から生成
4. レースでのエース差し替え（`isWorldStar`）→ 廃止。`worldRosters`の先頭が既に実質エース
   なので置き換え自体が不要。**④のバグも同時に消える。**
- 副産物：出走表の「🌍N位」バッジを**本物の世界順位**として出せるようになる。
- 後始末：`ml.worldSeed`を参照する箇所（`mlWorldNews`等）、`world/world.js`、
  `useMyLifeGame.js:160`、`state.js`の`worldStarTeams`、`components/panels.jsx:98`。

**2-E：バランス再較正（Phase 1の`seasonNeed()`と同じ手順）**
`worldRank`は野望の達成条件（`rankAtMost`）・殿堂評価（`breeding.js:126`の`worldRankBest`）・
キャリア推移グラフ・新聞見出しに直結する。実順位化で「世界1位」は600pt貯めれば取れるものから
**300人を実際に上回る必要があるもの**へ変わるため、難易度が大きく上がる。実測して
野望の目標値等を引き直す。

**旧セーブの扱い＝全員0から再スタート（ユーザー判断）**
`wp`不在の台帳は推定で埋めず、その時点から積み直す。**「全員」には自分も含める**＝
移行時に`ml.worldPoints`も0にリセットする（自分の持ち点だけ残すと継続セーブで不自然に
世界上位に立つため。年度減衰×0.72があるので数年で妥当な位置に戻る）。

#### 検証計画（2-A〜2-Eの実装後に必ず実施）

1. 全300人の`wp`分布と実順位の妥当性（上位が実際に強い選手か・団子になっていないか）。
2. **野望の`rankAtMost`がキャリア序盤で達成可能か**（クラス係数3.5の副作用の確認）。
3. 幽霊エントリ（④）が新規に増えないこと。台帳サイズの推移。
4. 旧セーブ互換：`wp`不在・`worldSeed`参照箇所の除去でクラッシュしないこと。
5. マイライフのPlaywright回帰（複数年到達）＋`npm run build`。

**要対応（設計上の必然）→ 解決済み（2026-08・2段階の実装）**：現在の`worldRankTier()`は
**300位スケール**（1位／≤3／≤10／≤30／≤80／≤200／それ以下）だが、実際の世界人口は**72名**
だった。統合すると「世界200位」が存在し得なくなるため、**しきい値を引き直す**か
**人口を広げる**かの二択で、ユーザーは後者を選択（「人口を広げたい」）。

**第1段階（後に撤回）**：`WORLD_ROSTER_SIZE`を`data/teams.js`で8→34へ変更し、9チーム×34＝
306名で300位スケールに合わせた。既存の拡張方式（v46 #23で確立済み：`genWorldRosters()`の
初期生成数・rngストリームには触れず、`topUpWorldRosters()`が独立したrngストリームで末尾に
追記するだけ）を踏襲したため技術的には問題なく動作（`scratchpad/roster_pop.mjs`で実測確認）。

**ユーザー指摘**：「増えた人口はチームとしてどこに割り振られてる？」という質問への回答
（9チームに均等34名ずつ）を受け、「自チームと比べて人数が多くなりすぎるだろうし、違和感を
感じて欲しい」という懸念が示された。シーズンの自チーム所属枠上限は`ROSTER_MAX_BY_CLASS =
[12, 14, 16]`（B1/A/PRO）＝12〜16名であり、AIチーム1つが34名という規模はそれと比べて
明らかに過剰。

**第2段階（確定・実装済み）**：ユーザーとの対話で方針転換に合意（`AskUserQuestion`で
2点確認）：
1. 1チームあたりの人数＝**12名前後**（シーズンB1の所属枠上限と揃える）
2. 目標人口＝**300名規模を維持**（worldRankTier()の300位スケールとの整合を優先）→
   12名×25チームで到達させるため、**新規チームを16増やす**

`WORLD_ROSTER_SIZE`を12へ戻し、`MYLIFE_TEAMS`に16チームを追加して9→25チームへ拡張
（12×25＝300名）。`RIVAL_TEAMS`（シーズンのクラス構成・6チーム）は意図的に不変のまま
据え置いた＝シーズン側の昇降格・所属チーム一覧には一切影響しない。追加16チームの
spec/tier配分は既存9チームと揃えて機械的に決定（各spec＝5チームずつ、tier＝9/8/8）。

**新規追加チームがUIの選択肢を圧迫しないことの確認**：`MYLIFE_TEAMS`の全消費箇所
（`createChar.js`の出身チーム抽選・`support.js`のライバル所属抽選・`month.js`の移籍オファー
候補抽選）はいずれも「配列から1〜数件だけランダムに1つ選ぶ」用途であり、**プレイヤーに
全チーム一覧を見せて選ばせるUIは存在しない**ことをコード上で確認した上で実施。むしろ
移籍オファーの母集団が増えることで「同じ数チームの中をぐるぐるするだけ」感が薄れる
副次効果がある。

`WORLD_ROSTER_SIZE`はSeasonの`rivalRosters`（`RIVAL_TEAMS`6チーム）とも共有する定数のため、
12へ戻したことでSeason側も6×12＝72名に収まった（こちらも自チーム上限12〜16名と近い規模感
になり、同じ「違和感」を予防できている）。

`aiSquadN = Math.min(aiSquadNRaw, roster.length)`で実際のレース出走人数は`roster.slice(0, N)`
の上位のみ使うため（`state.js`/`support.js`）、ロースター深化・チーム数増加はレースの計算量・
出走人数に一切影響しない。Playwright回帰（マイライフ6〜7年到達・エラー/NaN/undefinedゼロ、
2回の実装段階でそれぞれ実施）・`npm run build`で確認済み。`worldRankTier()`・
`genWorldRosters()`のcount引数は最終的にどちらも無変更。

**注意**：`mlWorldStarsForYear`は「状態は`ml.worldSeed`のみ保存し毎回1年目から再計算」という
設計。これを捨てても`worldRosters`は既に永続化されているのでデータ的な損失は無いが、
`worldSeed`を参照している箇所（`mlWorldNews`等）の後始末が要る。

## 追補：マイライフの自チーム（teammates）をworldRostersへ統合（2026-08・実装済み）

**発端**：人口拡張（25チーム化）の完了後、ユーザーから「マイライフの自分のチームはどういう
扱いになっているか」「自チームも人数を揃えたほうがいい」「移籍しても全チーム名鑑と自チームの
整合性が取れるようにしてほしい」「選手の引退・新加入・成長衰えは自チーム／AIチーム問わず
起きているか」という一連の質問。

**調査で判明した現状（修正前）**：
- 自チーム＝プレイヤー＋固定チームメイト5人（`mlGenTeammates`で独立生成）。id+年シード
  （第10弾続きで対応済み）で年内は安定するが、**年を取らない・引退しない・成長衰えもしない**。
  AIチーム（`worldRosters`）は`ageWorldRosters()`で年次に加齢/成長衰え/引退/新人補充が回っているが、
  自チームの5人にはこの処理が一切かかっていなかった。
- 移籍すると5人は個別の入れ替わりではなく**丸ごと総入れ替え**（無関係な新顔をランダム生成）。
- 自分が今いるチームでも`worldRosters[自チーム名]`という**使われない並行ロースター**が裏で
  存在し続け、他チームと同じく毎年加齢されていた（実害は`buildMyLifeSim`の分岐で防がれて
  いたが、既存の「チーム名鑑」画面（`mylife_teamroster`）は`ml.teammates`だけを見るため、
  この2系統が食い違うリスクを構造的に抱えていた）。

**採用した設計（ユーザー承認：「この方向で進める」）**：`ml.teammates`の独立生成をやめ、
**そのチームの実在ロースター（`worldRosters[チーム名]`）から取る**方式へ統合。
- `mlTeammatesFromRoster(worldRosters, teamName, n=ML_TEAMMATE_COUNT)`（`state.js`）を新設。
  `ML_TEAMMATE_COUNT = WORLD_ROSTER_SIZE - 1 = 11`（プレイヤー本人+11=12名でAIチームと同数）。
  ロースターは既にbaseline降順（エースが先頭）なので`slice(0, n)`だけで済む。
- `createChar.js`（新規キャリア）・`career.js`の`mlChooseTeam`（移籍）ともに
  `mlGenTeammates`の呼び出しをこの関数へ置換。移籍は「行き先チームに既にいる実在の選手たち
  （今まで対戦相手として見てきた顔ぶれ）に合流する」形になった。
- `month.js`の年度末処理（`ageWorldRosters`実行箇所）で`teammates`も同時に取り直すよう追加
  （残留・移籍いずれの分岐でも反映されるよう両方のfinalizeYearEnd呼び出しへ`teammates:
  nextTeammates`を追加）。自チームで引退・新加入があれば専用のログ行を出す
  （背景で起きても気づけないと「本当に効いているのか」分からないため）。
  重複を避けるため、既存の「世代交代（他チーム分・上位3件）」ログは自チームを除外する形に変更。
- `buildMyLifeSim`の自チーム分岐（`isMyTeam && teammates`）は、以前は先頭1人だけ固定+4する
  近似処理だったが、`tm.baseline || 0`をそのまま使うAIチーム側と同じ式に統一。これで
  worldRosters側の成長衰えが実際の地力にも反映されるようになった。
- 旧セーブ移行（`loadMyLifeGame`）も、`worldRosters`があればそちらから取る形に更新
  （無ければ`mlGenTeammates`へフォールバック、既存の互換性は維持）。
- 副次的な品質改善：`topUpWorldRosters()`が末尾に追記した控え選手をソートしていなかった
  ため、baseline降順の前提が一部で崩れていた（`genWorldRosters`/`ageWorldRosters`は
  末尾で既にソート済みだった）。「先頭＝最強」を前提にslice(0,N)する全呼び出し側
  （出走メンバー選出・今回の自チームteammates選出）の正しさを揃えるため、ここにもソートを追加。

**検証**：
- `scratchpad/teammate_unify_check.mjs`：全25チームで11名固定、teammatesがworldRosters先頭
  11名と完全一致、移籍先チームの実在ロースターに合流し元チームと重複無し、baseline降順を確認。
- `scratchpad/teammate_aging_check.mjs`：同一チームを15年分`ageWorldRosters`で進め、

- Playwright：新規デビュー直後の「チーム名鑑」画面で自分+11名（計12名）が正しく表示される

  undefined漏れゼロ、最終年のteammates年齢が20〜34歳とばらけている（＝加齢/世代交代が
