# 第11弾：リーグ全体の流れの可視化（#25）＋ 敵味方の能力開示（#24）

**状態**：設計合意済み・実装待ち（2026-08）。対象は#25→#24。

**発端**：「現時点だとリーグ全体の動きや強い選手・チームなど、ゲーム全体の流れをユーザーが
把握しきれないのが面白さを損ねている」（#25）／「敵チーム・味方チームの選手の能力を
見られるようにしたい」（#24）。

---

## 調査で分かったこと

### 発見1（最重要）：シーズンの順位表は張りぼてだった

`domain/season/standings.js` の `computeStandings(g)` は、他チームのポイントを
**チーム名のハッシュから作った固定の強さ × 月進捗**で生成しているだけ。
状態を持たず、レース結果を一切参照しない。

実測（`scratchpad/standings_check.mjs`）：

| 自分のポイント | 他チームの順位表 |
|---|---|
| 0pt | レッドサンダー山陽:43 / ヴェロチタ京都:42 / … |
| 500pt | 同上（**1ptも動かない**） |
| 5000pt | 同上（**1ptも動かない**） |

月推移も 1月:6 → 4月:24 → 7月:43 → 10月:61 → 12月:73 と**完全な直線**。

**「リーグ全体の流れが把握できない」のではなく、シーズンには流れが存在しない。**
画面の文言「他チームも毎月ポイントを積み上げています」は実態と食い違っている。

### 発見2：マイライフには既に本物の土台がある

- `riderStats`（`state.js`・マイライフのみ）＝全出走AI選手の実成績台帳
  （kind: world / rival / teammate / protege、通算＋年別の races/wins/podiums/bestRank）
- `mlWorldRaceLite(ml, seed)`＝**自分が出走しなかった月のレースも裏で決着**させ、台帳に積む
- `mlWorldTeamStats(ml)` / `mlRiderStatsRows(ml)`＝チーム別・個人別の表示用整形（純関数）

つまりマイライフは#25が求める「誰が強いか・誰が伸びているか」に答えるデータを既に持っている。
**シーズンには`riderStats`の受け皿（`initGame`の`riderStats: {}`）だけがあり、一度も書かれない。**

### 発見3：マイライフの「二重世界」

同じ「世界」を指す集団が2つ並存している：

| | 実体 | 役割 |
|---|---|---|
| `worldRosters` | 8名 × 9チーム＝**72名**・永続・`ageWorldRosters`で加齢/引退/補充 | **実際にレースへ出てくる相手** |
| `mlWorldStarsForYear` | **24名**・`ml.worldSeed`から毎回1年目より再シミュレート | 世界ランキング表示用。殿堂の血の流入先 |

ランキング上位の選手は、実際のレースにはグレードに応じて時々AIチームのエース枠を
差し替える形でしか現れない（`worldStarTeams`）。だから「世界1位」と「いつも自分と
走っている強い相手」が噛み合わない。

### 発見4：#24（能力開示）の現状

- `domain/shared/forecast.js` の `raceForecast()`＝出走表の予想印（◎本命/○対抗/▲注目）。
  コース適性順に**上位5名だけ**印がつく。両モード共通の純関数。
- シーズンの自チーム一覧は `overall(r)` でOVR表示。
- **相手選手の個別能力を見る手段は無い。**

## 合意した設計（ユーザー判断・2026-08）

1. シーズンの順位表＝**実体化する**（選手個人台帳の追加までは今回スコープ外）
2. マイライフの二重世界＝**統合する**
3. #24の開示＝**「情報を得る行為」に紐づける**

### Phase 1：シーズンの順位表を実体化する

- `g.rivalPoints`（チーム名→累計pt）を新設し、セーブ対象に加える。
- **自分が出走したレース**：`sim.ranked` から各AIチームの着順に応じてポイントを配分し加算。
  配分は自チームと同じ物差し（既存の`PTS`テーブル×`GRADE_MUL`）を使う。
- **自分が出走しなかったレース**：マイライフで実績のある`mlWorldRaceLite()`と同じ方式
  （地形適性＋baseline＋ノイズでスコアリングして順位付け）をシーズン向けに横展開し、
  `rivalRosters`から決着させてポイントを積む。
- `computeStandings(g)`は`g.rivalPoints`を読む形へ。**旧セーブ（`rivalPoints`不在）は
  現行のハッシュ式をフォールバックとして残す**（互換性）。

**要較正（実装フェーズで必ず実測）**：現行は`need`（クラスの昇格必要ポイント）に対する
相対で強さを作っている。実体化するとAIの実獲得ポイントが`need`と釣り合う保証がない。
かつ順位表は`seasonRank()`→`champPromoteCut()`経由で**昇格ボーダーに直結**するため、
実体化で昇格難易度が動く。実測して配分係数を較正すること。

### Phase 2：マイライフの世界ランキングを実際の対戦相手から作る

- ランキングの母集団を`worldRosters`（実際に走る72名）＋自分＋ライバルへ変更。
- 指標は「今季の実績」＝`riderStats`の`byYear`（勝数・表彰台）を主、地力（baseline）を従とする。
- `mlWorldStarsForYear`が担っていた**「殿堂の血が世界へ流入する」役割は
  `worldRosters`側の世代交代（`ageWorldRosters`/`topUpWorldRosters`）へ移す**
  （そちらが本物の加齢・引退・補充を既に実装済みのため）。

**要対応（設計上の必然）**：現在の`worldRankTier()`は**300位スケール**
（1位／≤3／≤10／≤30／≤80／≤200／それ以下）だが、実際の世界人口は**72名**。
統合すると「世界200位」が存在し得なくなるので、**母集団の実サイズに合わせて
しきい値を引き直す**か、`WORLD_ROSTER_SIZE`を増やして人口を広げるかの判断が要る。
実装フェーズの最初にここを決めること。

**注意**：`mlWorldStarsForYear`は「状態は`ml.worldSeed`のみ保存し毎回1年目から再計算」という
設計。これを捨てても`worldRosters`は既に永続化されているのでデータ的な損失は無いが、
`worldSeed`を参照している箇所（`mlWorldNews`等）の後始末が要る。

### Phase 3：#24 能力開示を「情報を得る行為」に紐づける

- **シーズン**：既存のスカウト職（`STAFF_ROLES`のscout・Lv制）を開示ゲートにする。
  Lvが上がるほど他チーム選手の情報が段階的に開く（例：Lv0=印のみ／Lv1=OVR概算／
  Lv2=脚質別の強弱／Lv3=数値）。**既存のスカウト職に実質的な意味が生まれる**のが利点。
- **マイライフ**：対戦経験（`riderStats`に記録がある＝実際に走った相手）を条件に実績を開示。
  能力詳細をどの行為に紐づけるかは実装フェーズで決める（**取材アクションは§18で廃止済み**
  なので復活させない。既存の導線に乗せる形を探すこと）。

**Phase 1・2が終わってから着手する**：土台（実体のあるポイント・実績台帳）が無い状態で
「この選手は強い」と表示しても意味を持たないため。

## スコープ外（今回やらないと決めたこと）

- **シーズンの選手個人成績台帳**（`riderStats`相当）＝ユーザー判断でスコープ外。
  ただしPhase 3のシーズン側で「対戦した相手の実績」を出すには何らかの記録が要るため、
  必要になったら**最小限の記録（対戦済みidの集合など）に留める**こと。
  フルの台帳を足したくなったら、その時点で改めてユーザーに確認する。

   極端に動いていないか実測（`seasonRank`→`champPromoteCut`経由で昇格に直結するため必須）。
