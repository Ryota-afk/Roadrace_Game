## この弾の位置づけ — 新機能ではなく「未完成の仕組みを閉じる」

`controllers/mylife/month.js` の生活費導入時のコメントにこう書かれている：

> v27: 生活費・税負担。年俸が上がるほど生活水準・税負担も増し、手元に残る額は頭打ちになる。
> 高級車・住居のグレードにも維持費がかかる。**これによりキャリア後半に資金がダブついて
> 緊張感が失われる（＝ヌルゲー化）のを抑える**

**狙いは最初から存在していた。それを打ち消しているのが `month.js:259` のクランプ**：

```js
const money = Math.max(0, s.money + Math.round(s.salary / 12) + popIncome - livingCost);
```

`Math.max(0, ...)` により**所持金は絶対にマイナスにならず、不足分は黙って帳消しになる**。
購入は全て `s.money < price` でガード済みなので、赤字の発生源は生活費だけ＝つまり
「払えなければ払わなくてよい」状態。緊張感を作るはずの生活費が、無害化されている。

**赤字は実際に起こりうる設計になっている**（`domain/mylife/growthCap.js:91-96`）：

| 項目 | 式 | 最大 |
|---|---|---|
| 車の維持費 | `(carLv+1)*4` 万/月 | 16万/月（`carLv=3`） |
| 家の維持費 | `(houseLv+1)*4` 万/月 | 16万/月（`houseLv=3`） |
| 合計 | | **32万/月** |

対して**序盤（B1・大学卒）の手取りは約13.6万/月**（月収23.3万 − 税11.7万 ＋ 人気収入2万）。
つまり上位の車・家を早く買えば確実に赤字になるが、今はそれが無かったことになっている。

## 設計1 — コーチの段階化＋月給制

### ⚠️ 先に読む：バランス実測（ユーザーの懸念「練習効果の上限を上げると崩れないか」への回答）

実コード（`domain/shared/growth.js`の`growthFactor`/`addAb`、`domain/mylife/growthCap.js`の
`mlGrowthCap`）を直接importして測った結果、**当初案の`ML_COACH_MUL=[1,1.25,1.40,1.55]`は
危険と判明した**。ただし危険の中身は「天井が上がる」ことではない。

**① コーチは天井を上げない。** 天井は`mlGrowthCap`が決め、`growthFactor`が上限超過分を
急減衰させる（実測：能力115で倍率0.0047、能力108で0.0271）。focus能力の12年後の最終値は
現行Lv1(1.25)と1.55で**+1.72点しか変わらない**。

**② カンスト時期は動く。** 現実的なプレイ（年7回練習・機材なし・初期58）でのカンスト年：

| Lv3候補 | 1.25 | 1.30 | 1.33 | 1.35 | 1.40 | 1.45 | 1.50 | 1.55 |
|---|---|---|---|---|---|---|---|---|
| カンスト年 | 11 | 11 | 10 | 10 | 10 | 10 | **7** | 7 |

**1.45と1.50の間に崖がある。** 1.40までなら現行から1年しかずれない。

**③ 本当の危険はfocus以外の能力にある（これが決定的）。**

| コーチ倍率 | 1.00 | 1.25 | 1.40 | 1.55 |
|---|---|---|---|---|
| focus以外の能力・12年後（熱心プレイ） | 101.2 | 111.0 | 116.1 | **120.4** |

focus以外は伸び係数が0.14（focusは0.9）と小さく**上限のはるか下に留まるため、倍率が減衰せず
丸ごと効く**。5人全員を高Lvにすると全能力が一様に押し上がり、**「極めると全員同じ万能型になる」
問題が再来する**——これは本プロジェクトが既に2回対処した問題（v46の突破力感度強化、
第29弾の`ML_TYPE_CAP_OFFSET`）。**倍率を上げる危険は天井ではなく均質化。**

**④ 副次的な観察（第36弾の対象外・別途要検討）**：熱心なプレイ（ローラー＋パワメ＋成長力A・
年10回練習）では**コーチが無くても3〜4年目、成長力Sなら2年目にfocus能力がカンストする**。
その条件下ではコーチは主因ではない。DEVLOG §38で一度対処した「早期カンスト」が別経路で
再発している可能性があり、気になるなら独立した弾で扱う。

### 定数（`src/data/gear.js` に追加）

上記を踏まえ、**ユーザー選択「両方やる」**＝倍率を緩め、かつ同時雇用数にも上限を設ける。

```js
// 第36弾: 専門コーチの段階制。シーズンのスタッフ（STAFF_MAX_BY_CLASS/STAFF_SALARY_PER_LV）を
// 手本にしているが、マイライフの家計スケールはチーム予算と桁が違うため、値は意図的に別で持つ
// （economy.js側を触るとシーズンのバランスまで動いてしまうため共有しない）。
// 倍率は実測で較正済み：1.50以上にすると現実的プレイのカンストが11年目→7年目へ跳ぶ崖があり、
// またfocus以外の能力は上限のはるか下で倍率が丸ごと効くため、上げすぎると全能力が一様に
// 伸びて「極めると全員同じ万能型」が再来する（詳細は上の実測節）。
export const ML_COACH_MAX_BY_CLASS   = [1, 2, 3];        // Lv上限：B1 / A / PRO
export const ML_COACH_SLOTS_BY_CLASS = [1, 2, 3];        // 同時に雇える人数：B1 / A / PRO
export const ML_COACH_MUL    = [1, 1.25, 1.33, 1.40];    // Lv0..3 の練習効果倍率
export const ML_COACH_SALARY = [0, 6, 10, 15];           // Lv0..3 の月給（万円/月）
export const ML_COACH_SIGNING = 100;                      // 契約金（Lv0→Lv1のときのみ）
```

**同時雇用数の上限が均質化への主たる歯止め**になる。5人全員を雇えなくなるため、
「どの能力を伸ばすか」の選択が生まれ、脚質ごとのシルエットが保たれる。
最大月給はPROで3人×Lv3＝**45万/月**（車家32万を足して77万/月）。

**⚠️ この組み合わせが生む既知のトレードオフ（実装後に必ずプレイで確認する）**：
倍率を緩めた結果、**Lv2・Lv3の費用対効果が悪い**。Lv1(1.25)に対しLv3(1.40)は相対+12%でしかないのに
月給は2.5倍。同時雇用数に空きがあるうちは「Lv1のコーチを増やす」方が常に有利になり、
**Lv2・Lv3が死に選択肢になりうる**。現時点では次の理由で許容している：
- 雇用枠が埋まった後（PROで3人雇った後）は、残る投資先がLv上げしかない。
- 終盤の余剰資金の吸収先（＝本弾の目的のひとつ）としては、小さい上乗せでも機能する。
- 赤字ペナルティと組み合わさることで「月々の固定費を上げる決断」自体にリスクが生じる。

それでも死に選択肢のままなら、**倍率ではなく月給側を下げて調整する**（倍率を上げると
上記③の均質化に直結するため、触ってよいのは月給の方）。

### 状態

- 新フィールド `ml.coaches = { flat: 0, climb: 0, sprint: 0, stamina: 0, solo: 0 }`（能力キーごとのLv）。
  `ML_SAVE_FIELDS`（`state/mylifeState.js:156`付近）に `"coaches"` を追加する。
- **既存セーブは無移行で保護する**：`ml.gear[coachKey]`（買い切り済み）はそのまま残し、
  効果判定を次にする（`month.js:113` と `:149` の2か所）：
  ```js
  const coachLv = (k) => Math.max(s.gear[ML_AB_COACH_KEY[k]] ? 1 : 0, (s.coaches?.[k] || 0));
  const coachMul = (k) => ML_COACH_MUL[coachLv(k)];
  ```
  ⚠️ **旧セーブで購入済みのコーチは月給ゼロのLv1相当が続く**（100万を払い済みのため遡って
  課金しない）。新規プレイヤーとの非対称は承知の上で、セーブ破壊を避ける方を採る。
- 新規の雇用は `ml.coaches` にのみ入る（`ml.gear` へはもう書かない）。

### 操作

雇用中の人数は `hired = Object.values(ml.coaches).filter(lv => lv > 0).length` で数える。

| 操作 | 条件 | 効果 |
|---|---|---|
| 雇用（Lv0→1） | `ml.money >= ML_COACH_SIGNING` **かつ `hired < ML_COACH_SLOTS_BY_CLASS[ml.classIdx]`** | `money -= 100`、`coaches[k] = 1` |
| 昇格（Lv→Lv+1） | `coaches[k] < ML_COACH_MAX_BY_CLASS[ml.classIdx]` | 契約金なし。月給が上がるだけ |
| 解雇（Lv→0） | 雇用中 | `coaches[k] = 0`。契約金は返らない。**枠が1つ空く** |

**降格（Lvを1つ下げる）は作らない**——複雑さに見合わない。解雇して雇い直す。

**⚠️ クラス降格時の扱い**：PROからAへ落ちると `SLOTS` と `MAX` が下がり、
**既に雇っている人数・Lvが上限を超える状態が起こりうる**。この場合は
**強制解雇や強制降格をしない**（プレイヤーの資産を勝手に奪わない）。上限超過の間は
「雇用・昇格ができない」だけとし、UIに現在値と上限を併記する（例：`3 / 2人`）。
赤字が続けば設計2の段階3が維持費の高いものから自然に整理する。

## 設計2 — 赤字ペナルティ（段階的）

### 前提の変更

`controllers/mylife/month.js:259` の `Math.max(0, ...)` を**外す**：

```js
const money = s.money + Math.round(s.salary / 12) + popIncome - livingCost;
```

これにより所持金がマイナスになりうる。**購入は既存の `s.money < price` ガードで自動的に
できなくなる**（シーズンと同じ副作用。新しいルールは足さない）。

### 状態

新フィールド `ml.debtMonths`（連続赤字月数・整数）。毎月末に
`money < 0 ? debtMonths + 1 : 0` で更新。`ML_SAVE_FIELDS` に追加する。

### 段階

| 段階 | 条件 | 内容 |
|---|---|---|
| 1 | `debtMonths === 1` | 警告表示のみ（＋買い物不可＝既存ガードの副作用） |
| 2 | `debtMonths` 2〜3 | 上記＋**生活が乱れる**：`form -6`／`managerEval -1.5`（各月） |
| 3 | `debtMonths >= 4` | 上記＋**強制的に手放す**（下記） |

**段階2の数値の根拠**：`form`は50が平常の0〜100スケールなので-6は体感できるが1か月で致命的ではない。
`managerEval`の通常の月次変動は`passiveEvalDelta`で±0.4程度（`month.js:251`）なので、
-1.5は「通常の4か月分を1か月で失う」重さ。いずれも**実装後にプレイして再較正する前提の初期値**。

### 段階3：強制的に手放す（自己修復の仕掛け）

**毎月1つだけ、「維持費が最も高いもの」を1段階手放す。** 赤字の原因そのものを狙い撃ちするため、
放置しても自動的に維持費が下がり、**デススパイラルにならない**。

- 候補と維持費：車`(carLv+1)*4`／家`(houseLv+1)*4`／各コーチ`ML_COACH_SALARY[lv]`
- **同額のときの優先順位：車 → コーチ → 家**（家は生活の基盤なので最後まで残す）
- 車・家：`lv` を1つ下げ、**その段階の定価の50%を所持金に戻す**（中古売却）。
  `lv` が `-1`（未所有）になったらそれ以上は対象にしない。
- コーチ：`ML_COACH_SALARY` が最大のコーチの `Lv` を1つ下げる（Lv1なら解雇＝0）。返金なし。
- **手放すものが何も無い場合**：段階2の効果だけが続く（それが底）。ログには
  「手放せるものが無い」旨を出し、年俸が上がるか賞金が入るまで耐える形になる。

### ログとUI

- 月次ログに必ず1行出す（`log.push`）。実例：
  - 段階1：`【{year}年目 {month}月】今月は支出が収入を上回った。所持金がマイナスの間は買い物ができない`
  - 段階2：`【…】赤字が{debtMonths}か月続き、生活が荒れている（フォーム-6・監督評価-1.5）`
  - 段階3：`【…】維持できなくなり{手放したもの}を手放した（+{返金}万円）`
- **ヘッダの所持金を赤くする**：`components/chrome.jsx` の所持金表示を
  `ml.money < 0 ? T.color.bad : T.color.accent` にする。
  ⚠️ **第35弾との依存**：第35弾で所持金を`head`／`accent`へ昇格させるので、
  この条件分岐は**第35弾の実装後に、その色指定へ被せる形で入れる**こと。
- ホーム画面に赤字の警告行を出す（`bad`色・`caption`）。文面はシーズンの
  `status.jsx:64` に倣い、**マイライフ用に言い換える**（「賞金とスポンサー収入で返済しましょう」）。
