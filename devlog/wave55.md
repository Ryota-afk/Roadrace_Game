## 発見1：「地形で決着の形が変わる」は**すでに実現している**

+10秒以内の人数が **平坦24〜26人 → 丘陵15人 → 山岳8人** と、地形によって決着の規模が
きれいに3段階に分かれている。**ユーザーが目指すと言った形（山岳＝少人数・平坦＝大集団
スプリント・丘陵＝中集団）は、集団規模という意味では既に達成されている。**

→ **不足しているのは「規模」ではなく「独走」。** 勝者の独走割合は山岳でも2.9%、
**逃げ切り勝ちは全地形で0.0%**。山岳で「独走で決まる」絵が一度も出ていない。
つまり第52〜55弾で追ってきた課題は、**全地形の問題ではなく「山岳で独走が起きない」
という一点に絞れる**。

## 発見2：未完走率は地形固有のバグ

未完走率が **平坦3〜4% / 丘陵7% / 山岳20% / ヒルクライム71%** と、登坂系だけが破綻している。
原因は明白で、`MAX_TICKS = 2500`が**固定値**なのに対しレース長が2198〜3217秒と地形で
大きく違うため。登坂は`terrainSpeedMul`（climb 0.65 / mtn 0.6）で遅く、
**ヒルクライムは平均3217秒＝tick予算を700秒超過している**。
超過分は`finishTime = MAX_TICKS + (remain / lastDist)`という**外挿**で埋められており、
着順がシミュレーションではなく外挿式で決まっている。

→ `MAX_TICKS`をコース長・地形から算出する形に変えるのが素直な直し方。
これは「3割が完走できていない」というユーザー指摘そのものの原因である。

## 発見3：「先頭1.0以内の人数」は序盤に暴れる

推移（20%→40%→60%→80%）が 10.9→24.8→9.2→17.5 のように非単調。
これは`role:"breakaway"`のAIがtick 0で自動アタックして先頭に出るため、序盤は
「先頭」が逃げの選手になり本隊が1.0圏外に落ちる（＝人数が少なく見える）ことによる。
⚠️**この指標を「選抜の進み方」として読むときは、序盤の値を額面どおり受け取らないこと。**

# 逃げの「形」の実測と、構造の根本原因（2026-08・Opus）

ユーザーの指摘：**「逃げにも単独逃げと集団逃げ（ブリッジで合流する形／初めから数人で逃げる形）が
あるのは考慮できてる？」**

**考慮できていなかった。しかも測定自体が壊れていた。** 従来の「逃げ切り」判定は
`mode === "solo" || "attack"` の割合で見ていたが、**2人以上で逃げる選手は自分たちで1グループを
作るためmodeは`pull`/`draft`になる**。つまり**集団逃げは最初から一切カウントされていなかった**。
「逃げ切り0.0%」という報告は「単独逃げが0%」としか言っていない誤報だった。

## 測り直し（本隊＝最多人数のグループとの位置関係で判定・n=40）

| テンプレート | 本隊で決着 | 単独逃げ | **集団逃げ** | ブリッジ発生率 |
|---|---|---|---|---|
| クリテリウム（平坦） | 95.0% | 0.0% | **5.0%** | 100% |
| サーキット（平坦+丘） | 97.5% | 0.0% | **2.5%** | 100% |
| 丘陵ロード | 95.0% | 0.0% | **2.5%** | 100% |
| 山岳ロード | 97.5% | **2.5%** | 0.0% | 100% |
| ヒルクライム | 100% | 0.0% | 0.0% | 73% |

集団逃げは実際に2.5〜5%で決まっており、ブリッジも全レースで発生していた。
**弱いながら形は既に正しい方向を向いている**——集団逃げが決まるのは**平坦**、
単独逃げが決まるのは**山岳**で、実際のロードレースと同じ対応になっている。

**この測定の限界**：「先行集団の最大人数」が平均11〜16人・最大26人と出たが、これは
**フィールドの分裂を先行集団と誤認している**（判定が「最多人数のグループより前にいる集団」
なので、集団が二分割されると前半分が先行扱いになる）。⚠️**この数字は信用しないこと。**

## 決定実験：集団の速度は人数に一切依存しない

同一能力・同一シードで人数だけ変えて500tick走らせた（`scratchpad/w55_coop.mjs`）。

| 人数 | 500tick後の位置 | 残脚 |
|---|---|---|
| 1人 | 98.1 | **−100.0** |
| 2人 | 119.3 | −55.4 |
| **3人** | **126.6** | 43.4 |
| **6人** | **126.8** | 90.9 |
| **12人** | **126.6** | 91.6 |
| **24人** | **126.6** | 91.2 |

**3人以上は速度が完全に同一（126.6）。人数は速度に1ミリも効かず、効くのは残脚だけ**
（43.4→90.9で飽和）。1人だけ遅いのも「単独走が遅い」からではなく、脚が−100まで枯れて
`energyPenaltyMul`が0.55倍に張り付くため。**速度式は全員同じ**。

原因は`ticks.js`の`const groupDist = puller.lastOwnDist;`——**集団の速度は「牽引者1人の全力」で
決まり、人数の項が存在しない**。

### これが第52〜55弾すべての空振りの正体

**逃げは時間差を作れない。** 本隊と同速なので、できるのは「同じ位置を保ったまま、より疲れて
ゴールする」ことだけ（3人の逃げは残脚43.4、本隊は91.2）。決着で負けて当然である。
**逃げが成立しない理由は、速度でも消耗の割引でもなく「協調に速度の見返りが無い」こと**
だった。第52弾（定数）・第53/54弾（集団のテンポ）・第55弾当初案（`brk`）はすべて
この本質を外していた。

ちなみに実測で**出走の24%がエース**で、エースは`canPull`で牽引から除外される
（ロール内訳は lead 28% / flat 24% / breakaway 21% / sub 20% / mountain 7%）。
つまり「牽ける人数」は総人数とは別物であり、**協調の質**を表す軸として既に存在している。

# 確定仕様（ユーザー合意済み・2026-08）

## 1. 協調による速度 `coopMul` を導入する（中核）

集団の速度を「実際に牽ける人数（`eligible`）」で決める。**飽和させるのが肝**——
飽和しないと本隊が常に最速になり、逃げが永久に成立しない。

```js
// ticks.js の集団ループ内。eligibleはローテーション用に既に計算済みのものを流用する。
const workers = Math.max(1, eligible.length);
const coopMul = 1 + COOP_MAX * (1 - Math.exp(-(workers - 1) / COOP_K));
// groupDist = puller.lastOwnDist * coopMul  （後述の適用位置に注意）
```

**定数（ユーザー承認済みのカーブに合わせて逆算した値）**：`COOP_MAX = 0.17`／`COOP_K = 3.15`

| 牽ける人数 | `coopMul` |
|---|---|
| 1 | 1.000 |
| 3 | 1.080 |
| 6 | 1.135 |
| 12 | 1.165 |
| 24以上 | 1.170（頭打ち） |

**単独走者（`members.length === 1`）は`coopMul = 1`**（`workers = 1`なので式からも自動的に1）。

## 2. 本隊の協調は「レースが進むほど」立ち上がる

**1だけでは逃げは今より不利になる**——本隊（牽ける人数20前後→1.168）が
逃げ（6人→1.135）より速くなってしまうため。実際のレースで逃げが成立するのは
**序盤の本隊が本気で追わないから**であり、それを「協調の質」として表現する。

`eligible`に**やる気のゲート**を掛ける：

```js
// 序盤は本隊の全員が追うわけではない。レースが進むほど組織的な追走になる。
const organized = Math.min(1, prog / CHASE_ORGANIZE_PROG);
const willingFrac = CHASE_EARLY_WILLING + (1 - CHASE_EARLY_WILLING) * organized;
```

- **逃げ（`committedBreak`の選手で構成される集団）にはこのゲートを掛けない**——
  覚悟を決めて出た選手は最初から全員が回す。これが集団逃げの速度優位の源。
- **選ぶ選手は決定論的に選ぶこと**（`riderHash01(en.id, salt)`で安定した順序付けをして
  上位`willingFrac`だけを`eligible`に残す）。`Math.random()`で選ぶとtickごとに顔ぶれが
  変わり、牽引ローテーションが崩壊する。

**定数（すべて仮置き・実装後にOpusが実測して確定）**：
`CHASE_EARLY_WILLING = 0.45`／`CHASE_ORGANIZE_PROG = 0.60`

これにより序盤は 本隊（20人×0.45＝9人→1.146）< 逃げ（6人全員→1.135）… まだ本隊が速い。
**この数値関係は設計段階では確定できない**（`eligible`の実際の分布が未知のため）。
実装後に`CHASE_EARLY_WILLING`を振って**序盤に逃げが本隊よりわずかに速くなる**点を探す。

## 3. `brk`（単独逃げの消耗割引）は据え置き、Phase 2で判断する

当初案の`brk`再較正は**この弾では入れない**。協調による速度が入ると前提が丸ごと変わり、
第54弾で測った「brk=0.22が最適」はすべて無効になるため。単独逃げ（山岳）が
まだ成立しないようなら、Phase 2で改めて測って決める。

## 4. `MAX_TICKS`の固定値問題は**この弾では扱わない**

未完走率（ヒルクライム71%・山岳20%）は`MAX_TICKS = 2500`固定が原因の**独立したバグ**
（発見2）。協調による速度でレース全体が速くなるため**自然に改善する可能性がある**。
まず協調を入れて測り直し、それでも残るならコース長からの算出式を別途設計する。

## やらないこと

- `attack`/`send`の定数・`mid`カード・`send`が最下位の件（§82）はこの弾では扱わない。
- `chaseMode`を展開に接続する件も扱わない。

## 予測と撤退基準（4回目なので実装前に明示する）

実装後にOpusが測る（`scratchpad/w55_shape.mjs`＋`w55_breaktype.mjs`＋`w54_sweep_one.mjs`）。

**成功の形**：

|---|---|---|
| 集団逃げで決着（平坦・クリテ） | 5.0% | **10〜15%** |
| 集団逃げで決着（丘陵） | 2.5% | **8〜12%** |

**撤退基準（1つでも該当したら協調による速度そのものを撤回する）：**

1. **`hold`の平均着順が基準から2着を超えて悪化する**（第53/54弾と同じ失敗）。

**欠陥1：牽引者が自分の集団から弾き出される（致命的）。**
移動パスは`pull`/`solo`/`attack`を先に処理し、そこで牽引者は**自分の出力`dist`のまま**
進む（`en.pos += dist`）。その後の集団ループでドラフト勢だけが`groupDist = dist × coopMul`

**牽引者は8tickほどで自分の集団の後ろへ千切れる**。これが毎回の交代で起き続ける。
（第52弾までは`groupDist === puller.lastOwnDist`だったため両者は完全に同速だった。
設計書の「`groupDist = puller.lastOwnDist * coopMul`（**後述の適用位置に注意**）」という
但し書きは、まさにこの点を指していた。）

残留判定は`ownCapable >= groupDist * keepThresh`。`groupDist`が17%増えた分、
残留の条件も17%厳しくなる。`keepThresh`の基準値0.9に対し実効0.9×1.17＝**1.053**＝
**ドラフト勢は牽引者より強くないと集団に残れない**。既存の選抜強化（`tempoTighten`0.06・
`selectiveTight`0.035）の10倍以上の締め付けで、**ドラフトの利点そのものが消えていた**。
設計の意図は「協調の見返り＝速度」であって選抜の厳格化ではないため、これは意図外の副作用。

## 撤退基準1：`hold`が5.00着悪化＝抵触

⚠️基準値12.93は別のコード状態で測ったものなので、**同一コードで`COOP_MAX`だけを
変えて測り直した**（`w55_sweep_one.mjs`）。

| `COOP_MAX` | `hold`(terrain) | 基準比 | `hold`(mid) | グループ数 | レース長 |
|---|---|---|---|---|---|
| **0.00**（協調なし＝真の基準） | **12.21** | — | 10.92 | 7.01 | 2685秒 |
| 0.04 | 15.22 | **+3.01** ⚠️ | 15.02 | 5.34 | 2617秒 |
| **0.08**（採用値） | **17.21** | ⚠️**+5.00** | 14.75 | 4.94 | 2543秒 |

⚠️**0.04（半分の強度）でも+3.01着で抵触する。** 基準（2着以内）を満たすには0.02程度まで
下げる必要があるが、その時の`coopMul`は6人で**1.016**＝逃げへの見返りが実質ゼロになる。

### なぜ`hold`が悪化するのか（機構の理解）

⚠️**残留判定は修正2で第52弾と同一に戻っているので、千切れやすさ自体は変わっていない。**
効いているのは**レースが短くなること**である：協調で集団が速くなる→レースが少ないtickで
終わる→**選抜が累積する時間が減る**→フィールドが圧縮される（グループ数7.01→4.94・−30%）
→**本来は千切れていた弱い選手がゴール勝負まで生き残る**→強い選手（実測は能力74＋バッジ3種）
の相対順位が下がる。

**つまり「`hold`基準の維持」と「逃げの成立」は同じレバー（レース速度）から出ており、
`COOP_MAX`の調整では両立しない。** 値が悪いのではなく**トレードオフが構造的**。

## 判定

⚠️**事前に宣言した撤退基準1に抵触した。** 前回の抵触は実装バグが原因だったが、
今回は**修正後・機構が正しく動いた上での抵触**であり、⚠️**「実装バグだったのでもう一度」は
使えない**（それを封じるために前回明記した）。

ただし今回わかったことは前回と質が違う：**協調の概念は機能した**（集団逃げが平坦12.5%・
丘陵15.0%で目標到達）。失敗したのは「速度で逃げを作ると、その副作用でレースが短くなり
選抜が減る」という**副作用の方**である。次の案を考えるなら、⚠️**レース全体の所要時間を
変えずに逃げと本隊の相対速度だけを変える機構**でなければ同じ壁に当たる
（第53・54弾のテンポも第55弾の協調も、結局すべて「レースの速度」を触っていた）。

## この4回で確定した2つの結論（次の設計の前提にする）

### 結論1：**速度を触るアプローチは尽きた**

4回とも「レースの速度」を触り、4回とも別々の理由で失敗した。

| 弾 | 何を触ったか | 失敗の仕方 |
|---|---|---|
| 第52弾 | `attack`等の定数 | 定数では動かない（構造の問題と判明） |
| 第53弾 | 集団ごとのテンポ | 先頭集団が最も遅くなりフィールドが融合 |
| 第54弾 | レース全体のテンポ | `hold`が3〜6着悪化・グループ数−24% |
| 第55弾 | 協調による速度 | `hold`が5着悪化（レースが短くなり選抜が減る） |

⚠️**第54弾の総括「フィールドの一部だけを速く/遅くする限り同じ現象が起きる」に加え、
第55弾で「フィールド全体を速くしても（レース時間が変わるので）同じく壊れる」ことが確定した。**
**速度という軸そのものが行き止まり。** 次に速度案を出しかけたら、この表を見ること。

### 結論2：**残る軸は「エネルギー経済」であり、それは既に測ってある**

⚠️このファイル冒頭の【失効】扱いにした`brk`単独の再較正は、**失効させるべきではなかった**。
第54弾の判定時の実測（テンポOFF・`brk`だけを下げる）：

| brk | terrain/hold | terrain: attack−hold | グループ数 |
|---|---|---|---|
| 現行 | 12.93 | +12.25 | 6.86 |
| **0.22** | **12.93（完全に同値）** | **+1.43** | **6.74** |

**`hold`が基準と完全に同値のまま`attack`が僅差の選択肢になった唯一の案**である。
理由も明確で、**集団に一切触らないので基準点が動かず、速度差を作らないので選抜も壊れない**
——第53〜55弾が壊したのは、まさにこの2つだった。

⚠️**ただしこの実測の「逃げ切り勝ち10.4%」は例の壊れた判定（`mode==="solo"||"attack"`＝
単独逃げしか数えない）で測った値**なので、集団逃げについては何も言っていない。
`brk`は`committedBreak`かつ`solo`/`attack`にしか掛からない＝**単独逃げ専用の機構**であり、
**山岳の単独逃げ（現状0.0%・目標10〜15%）にちょうど対応する**。
集団逃げ（平坦・丘陵）は別途の課題として残る。
