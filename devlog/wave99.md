## ユーザーが決めた2つの分岐（本弾の前提）

### 分岐1：賭けるものは「金と活力の両方」

提示した3案（活力のみ／金のみ／両方）のうち**両方**を選択。

- **金**：31-C の「使い道を足すのではなく競合させる」に乗る。開発・科学トレと同じ財布を取り合う。
- **活力**：`player.vitality`（0〜100）。`vitMul = 0.55 + 0.45*min(1, vit/70)`
  （`controllers/mylife/month.js:36`）で、**70を割ると練習・出走経験の伸びが鈍る**。
  現状の消費はレース1回で `5 + grade*2`（7〜13）、練習3、完全休養+22、オフシーズン+20〜40。
- ⚠️**この組み合わせが持つ自己矛盾が、そのまま緊張になる**——本気度の見返りは成長であり、
  支払うのは「成長の芯」である。育てるために育つ力を削る。

⚠️**第93弾の実測が従来方針の根拠を崩していたことを記録しておく。** TODO 32-d には
「賭けるのは金（#16の恒久シンク不足を埋める）」とあったが、第93弾では
**シンクを使うプレイヤーは吸収力3,100万/年 対 純収入1,600万/年＝常に資金不足**と判明して
いる。つまり「余った金の捨て場」という動機は成立しない。金を賭ける意味は
**「余りを捨てる」ではなく「開発と取り合う」**である。

⚠️**懸念（未解決・UI設計で解く）**：コストが2種類あるとUIが重くなり、CLAUDE.md §7の
引き算原則と衝突する。**「本気度」というつまみ1つに対して結果が2行出る**形にはしない。
候補提示（§8手順1）の段階でここを主要な争点として扱う。

### 分岐2：構造は「賭け型（閾値で払い戻し）」

提示した2案（購入型／賭け型）のうち**賭け型**を選択。

- 出走前に本気度を上げると、**目標**（例「3位以内」）が宣言され、相手が強くなる。
- 達成すれば大きな見返り。**外せば賭けたものは没収され、見返りはゼロ。**
- 購入型（着順に関わらず倍率が付く）を却下した理由：CLAUDE.md §0-1 の

## 実装レバー（新しいsim機構は不要）

  `DIFFICULTIES.find(d => d.id === difficultyId)` から `aiMul` と `abilCap` を引くだけ

  「別の（もっと強い）選手が来る」ではなく**「同じ顔ぶれが本気を出す」**という意味論に

### 置き場所の技術的制約（調査済み）

- `mlStartRace`（`hooks/useMyLifeGame.js:202`）が **出走表を出す前に sim を組み終えている**
  （`ml.result = sim`）。
- したがって本気度を**出走表の画面で**動かすなら、`buildMyLifeSim` の再実行が必要。
  ⚠️**これは既に確立した挙動**——`RaceView`の判断カードが選択のたびに再simしている
  （`resimBusy`）。1回のsim再構築は実測 **約315ms**。
- 出走表で決められると、**本気度を上げると出走表の顔ぶれが実際に強くなるのが見える**

### ⚠️しかし人気度だけでは賭けが成立しない（コード読解＋数値換算で確定）

`popularity`の全参照を追跡した結果、影響先は**3つだけ**だった：

| 経路 | 実体 |
|---|---|
| 月収 | `popIncome = floor(popularity/10)*2` 万/月（`month.js:257`）⚠️**10刻みで量子化** |
| 到達ボーナス | `POP_MILESTONES` 25/50/75/100 → 80/150/250/400万（一度だけ・**生涯合計880万**）|
| 新聞の文面 | フレーバーのみ（`worldRank.js:244`）|

⚠️**年俸・契約・世界ランク・CPには一切影響しない。** さらに`popAdd`
（`domain/mylife/popularity.js`）が**逓減**を掛ける（`eff = delta * (1 - pop/100)`）。
これは第87〜90弾の「人気度100張り付き」修正の中核なので、⚠️**外すと過去のバグが再発する**
（第90弾は4箇所の素通りを塞いだ弾だった）。

**円熟PRO・人気度50・グレード3でレベル2（560万）を賭けて表彰台に乗った場合**：

- 素の`popGain` = 1.5 × `GRADE_MUL[3]`(=2) = 3 → 逓減後 **+1.5**
- 2.4倍にしても 7.2 → 逓減後 **+3.6**。差分は**約+2人気度**
- ⚠️`floor(pop/10)`の量子化で**月収が1円も動かないことが多い**
- 生涯価値に換算して約70万。成功率23%なので ⚠️**期待値 約17万 対 賭け金560万＝約30倍の劣位**
- 賭け金を60万まで下げても3.5倍の劣位で足りない

⚠️**プレイヤーは絶対に選ばない＝§0-1が禁じる「承認するだけの操作」そのものになる。**

## #32-kの原因調査（本気度の依存を外すために実施）

### 仮説と、その一部支持

`raceForecast`は`favors`（レース1つにつきラベル1つ）から固定の式を引く
（`FAVORS_TO_DISCIPLINE`→`DISCIPLINES[key].calc`。RULなら`flat*0.6 + solo*0.25 + stamina*0.15`）。
一方simは**実際のコースの区間構成**（`SEG_AB`）で走る。グラベル（RUL扱い）に`tt`区間が
ほぼ無ければ`solo*0.25`は架空の重みになる。

⚠️**B1帯だけ偏る理由の説明**（実測）：

| | flat | climb | sprint | stamina | solo |
|---|---|---|---|---|---|
| B1 プレイヤー | 73 | 51 | 48 | 66 | 48 |
| B1 AI平均 | 66 | **65** | **62** | 64 | **65** |
| PRO プレイヤー | 104 | 98 | 79 | 106 | 74 |
| PRO AI平均 | 76 | 75 | 73 | 75 | 74 |

⚠️**B1は「専門型のプレイヤー vs 万能型のAI」**（AIは全能力が64〜65でほぼ平ら）。式がずれると
**専門型だけが大きく誤査定される**。PROではプレイヤーが全能力でAIを圧倒する（104 vs 76）ため、
どの式でも上位に並び偏りが出ない。

### ⚠️対照実験の結果——仮説は一部のみ支持、提案した式は不採用

同じ出走者に対し①現行の`favors`式 ②実コースの区間構成から作った式（距離按分＋stamina一律15%）
の2通りで予想順位を出し、実着順に対する「予想超え率」を比べた（`scratchpad/fc_cause.mjs`）。

| | 実着順 | ①現行 | ②区間構成から |
|---|---|---|---|
| 新人 B1（n=200）| 18.88 | 予想25.53・**77%** | 予想21.89・**65%** |
| 円熟 PRO（n=168）| 7.38 | 予想7.20・**44%** | 予想5.00・**32%** |

- ⚠️B1は77%→65%で**偏りの半分弱しか埋まらない**（目標50%）。
  favors/区間のずれは**寄与の一部**であって全部ではない。
- ⚠️**PROは44%→32%と、ほぼ公平だったものを逆方向へ壊した。** 「staminaを一律15%」という
  こちらが置いた重みが、stamina 106のPROプレイヤーを過大評価している。

⚠️**したがって#32-kは20〜30行の修正ではない。** 原因の一部は掴めたが直し方が定まっていない。
残る候補：チームメイトの風除け（プレイヤーは3人のチームメイトを持つエース）が予想式に無い／
装備・バッジ／そもそも純粋な能力式では公平にできない（sim側の結果が展開・エネルギー・
判断カードに依存するため）。⚠️後者なら、直すべきは式ではなく**見せ方**（順位の断定をやめる）。

### 本気度は#32-kを待たずに進められる

⚠️**案Cが使っているのは印の絶対値ではなく「変化」である。** #32-kの偏りは**水準のずれ**であって
**向きの誤り**ではない（実測：本気度0/+0.06/+0.12で下馬評1番手/3番手/5番手と単調に落ちる）。
「◎が他人に移った＝相手が強くなった」はB1でも正しく伝わる。

⚠️**条件は1つ**——本気度の実装で**予想順位の絶対値を主張する新しい文言を足さないこと**
（「あなたは12位予想です」のような断定）。既存パネルの表示に手を触れなければ嘘は増えない。

### （旧）先に直すべき依存：#32-k

⚠️案Cは**下馬評を判断材料として重くする**が、下馬評はB1帯で約7着ぶん悲観的（本弾の副産物）。
⚠️**#32-kを先に、または同時に直すこと。** 直さないとB1のプレイヤーは
「◎本命なのに勝てない」ではなく「無印なのに勝てる」という逆の嘘を見せられたまま賭けることになる。

### ⚠️追加で発見・解決した問題：`buildMyLifeSim`のRNGがDate.now()由来だった

案Cの前提は「同じ顔ぶれのまま相手が本気を出す」ことだが、`buildMyLifeSim`内部の
`const rng = mulberry(Date.now() % 999983)`は**呼ぶたびに違う乱数列**を生成する。
本気度を選び直すたびにこの関数を呼び直す設計のため、**何も対策しなければ選び直すたびに
出走者の人数・チーム構成・当日の調子まで無関係に入れ替わってしまい**、UIの前提（「同じ顔ぶれ」）
が崩れる。

対策として`buildMyLifeSim`に17番目の引数`seed`を追加し、省略時は従来どおり`Date.now()`を
使う（既存呼び出し元は無変更で動く）。`mlStartRace`が最初の出走表表示時に1回だけ
`Date.now()`から`raceSeed`を確定して`ml`に持たせ、`mlSetIntensity`は毎回**同じ`raceSeed`**を
渡して再構築する。

⚠️**この対策が成立する根拠を実装前に検証した**（`newRider`のコードを読んだ上で、実際に
同じseed・違うintensityで2回ビルドして比較）：

```
人数一致: true 40 40
名前の集合一致: true
チーム構成一致: true
AI能力の平均差分(intensity1-0): 3.45 （正なら強くなっている）
同一入力の再現性: true
```

`newRider`が消費する乱数の回数は`power`（本気度で動く値）に依存しない
（型判定・能力5個・年齢・成長タイプ・特殊能力・性格の各抽選は、抽選の**結果**は`power`と
無関係で、抽選の**回数**も分岐条件が`power`を参照しない）ため、同じseedなら同じ乱数列が
同じ順番で消費され、`power`だけが変わる。

⚠️**閾値は能力60/80/92で較正したが、実キャリアはそこを4〜5年目に追い越す。**

| 年目 | 総合力(中央値) | 資金(中央値) | 活力(中央値) |

- `betSmart`（活力78以上のときだけ張る）は⚠️**1440レース中0回発火**。活力の中央値は
  10年目で30、15年目で20——⚠️**毎月レースに出るキャリアで活力は常に枯れている**
  （`vitMul`が恒常的に0.68付近）。活力を条件にした賭けは成立しない。

⚠️**第1回（n=8）で「賭けた側が総合力+9・勝利+24で上回った」と報告したが、これは撤回する。**

|---|---|---|

埋めてしまう。⚠️**第1回の1本だけを見て結論を出しかけたのは、本セッションで4度繰り返した

一方で⚠️**達成率80%・81%は2つの独立した方策アーム（n=111とn=47の賭け）で一致しており、
こちらは信頼できる。**

`builder_bet1`のcareer3で⚠️**A3違反（資金マイナス12ヶ月連続）が1件**出た。賭けなしの
`builder`は13本中0件。n=1なので断定はできないが、⚠️**賭けが「奪う側」として実際に

### ⚠️結論：合格条件を満たしていない。倍率の較正ではなく閾値の設計から直す必要がある

合格条件は「レベル0/1/2が条件によって非支配」だったが、⚠️**達成率80%では賭けは
「押すだけ得なボタン」に近い**（§0-1が禁じる「承認するだけの操作」）。しかも
⚠️**倍率をいじっても直らない**——問題は払い戻しの大きさではなく、
**目標が実キャリアの強さに対して緩すぎる**ことだから。

| `aiMul`差 | 勝率 | 3位以内 |
|---|---|---|
| +0.00 | 86% | 91% |
| +0.50 | 73% | 85% |
| +1.00 | 72% | 89% |
| **+2.00** | 64% | **80%** |

⚠️**3倍にしても表彰台率は91%→80%しか動かない＝この帯でつまみは無反応。**
`newRider`が各能力を`aiCap`(96)でクランプするため、`power`を上げても上限に
押し付けられる選手が増えるだけ。Δ秒も−79→−104で頭打ちになる。

⚠️**設計時に選んだ「`abilCap`は触らない＝同じ顔ぶれが本気を出す」という意味論そのものが、
案Bを不可能にしていた。** 案Bを推薦した時点でこの相互作用を確認していなかったのは誤り。

### ⚠️発見2：`aiCap`単独でも効かない（機構上の理由）

PRO帯のAI能力の実測平均は約75で、⚠️**上限96に20ポイント余っている**
（`aiPowerFor(50,2,3,1.0) = (50+18+8)*1.0 = 76`）。⚠️**当たっていない天井を上げても
何も起きない。** 両方を同時に上げる必要がある。

### ⚠️発見3：`--chars 4`では標本が足りない（自分の報告を1つ撤回）

同一条件（能力120・AI上限140・`aiMul +0.00`）が別々の実行で**77%と98%**になった。
`mlCreateChar`が非決定論的なため、⚠️**88サンプルに見えても独立した標本は4キャラしかない。**
⚠️**「AI上限を140まで上げても85%→77%しか動かない」という報告は撤回する**——実行をまたいだ
比較でノイズに埋もれる差だった。⚠️**同一実行内の段の比較は対応のある標本なので信頼できる**
（プローブは同じキャラ・同じレースを全段へ流している）。以降は`--chars 10`で測った。

### 較正の本番（AI上限140・10キャラ・対応のある標本）

| 3位以内 | 総合力111 | 総合力134 | 総合力157 |
|---|---|---|---|
| `aiMul +0.00` | 57% | 86% | 100% |
| `+0.10` | 42% | 71% | 99% |
| `+0.20` | 20% | 56% | 95% |
| `+0.30` | 10% | 30% | 87% |
| `+0.45` | 0% | 11% | 58% |

⚠️**必要な`aiMul`は強さに対して超線形に増える**（40%到達に必要な値：総合力111で+0.11、
134で+0.27、157で+0.55）。線形の係数では上の帯で足りない。

### ⚠️発見4（設計の鍵）：勝敗を決めているのは「AI power ÷ プレイヤー能力」の比

`power = aiPowerFor(50, classIdx, grade, diffAiMul) = (50 + classIdx*9 + (grade-1)*4) * diffAiMul`
なので、上の15セルを比で並べ直すと⚠️**強さが違っても比が同じなら達成率がほぼ一致する**：

| power÷能力 | 3位以内 | 出典 |
|---|---|---|
| 0.53 | 100% | 総合力157 / +0.00 |
| 0.63 | 95% / 86% | 157 / +0.20、134 / +0.00 |
| 0.70 | 71% | 134 / +0.10 |
| **0.76** | **56% / 57%** | ⚠️**134 / +0.20 と 111 / +0.00 がほぼ一致** |
| 0.765 | 58% | 157 / +0.45 |
| 0.82〜0.84 | 30% / 42% | 134 / +0.30、111 / +0.10 |
| 0.91〜0.92 | 20% / 11% | 111 / +0.20、134 / +0.45 |
| 1.10 | 0% | 111 / +0.45 |

セル間には±10〜15ポイントのばらつきが残る（段階ごとに独立な10キャラを引いているため）が、
⚠️**比が単調に効いていることは明らかで、絶対値の`aiMul`より遥かに素直に説明できる。**

### ⚠️結論：つまみは「比」で表現すべきだった（案B'）

強さごとに`aiMul`の係数を当てはめる（案B）のではなく、⚠️**「本気を出した相手はあなたに
対してどれくらいの格か」を段が決める**形にすれば、式のフィッティング無しで自動的に
スケールする。実装は`diffAiMul`を逆算するだけ：

```
targetPower = プレイヤーの能力平均 × RATIO[level]
diffAiMul   = targetPower / (50 + classIdx*9 + (grade-1)*4)
aiCap       = プレイヤーの能力以上へ引き上げる（でないとクランプで死ぬ）
```

比の目安（上表から）：**RATIO[1] ≈ 0.76（達成率55%前後）／RATIO[2] ≈ 0.85（30%前後）**。

⚠️**必須のガード**：弱い選手（新人・能力60）では`60 × 0.76 = 45.6`となり、
⚠️**素の`power`（76）より弱くなる＝賭けたのに相手が弱くなる**。
必ず`max(素のpower, targetPower)`を取ること。

⚠️**意味論の変化**：「同じ顔ぶれが本気を出す」→「あなたと同格の相手が出てくる」。
ただし`mlAiCapFor`は既に難易度で上限を動かしており（易92／普通96／ハード102／鬼112）、
⚠️**本気度が同じことをするのは新概念の追加ではなく既存パターンの踏襲**である。
下馬評が動くというUIの根拠（案C）はむしろ強くなる。

## 案B'の設計図（ユーザー合意済み・実装はSonnet）

### 式

```js
// 1. 素の集団（賭けなければこうなる）。従来どおり。
const naturalPower = aiPowerFor(50, classIdx, raceMeta.grade, diffDef.aiMul);
// 2. プレイヤーの能力平均（buildMyLifeSimが受け取るplayerの生の能力。装備・バッジ適用前）
const playerAbil = AB_KEYS.reduce((a, k) => a + (player[k] || 0), 0) / AB_KEYS.length;
// 3. 段が「相手の格」を比で決める。⚠️max()が必須——弱い選手では比を掛けると素より
//    弱くなり「賭けたのに相手が弱くなる」ため。
const ratio = INTENSITY_POWER_RATIO[intensity] || 0;
const power = ratio ? Math.max(naturalPower, playerAbil * ratio) : naturalPower;
// 4. 上限を上げないとクランプで死ぬ（発見1）。newRiderの最大生成値は power+11+脚質補正14。
const baseAiCap = mlAiCapFor(difficultyId, diffDef.abilCap);
const aiCap = ratio ? Math.max(baseAiCap, Math.round(power) + 26) : baseAiCap;
```

⚠️`diffAiMul`への加算（現行の`INTENSITY_AIMUL`）は**廃止**する。`diffAiMul`は
`aiPowerFor`の1箇所でしか使われていないので差し替えは局所的。

### 比の値と、それが狙う達成率

**`INTENSITY_POWER_RATIO = [0, 0.82, 0.90]`**

較正表（比→3位以内）から：比0.82〜0.84で30%/42%（平均約36%）、比0.91〜0.92で20%/11%
（平均約16%）。素の比はキャリアで **0.83（新人B1）→0.76（能力100）→0.53（能力144）**と
**下がっていく**（これが早期カンスト問題の言い換え）ため、比を絶対値で置くと：

| 選手 | 素の比 | 段1(0.82) | 段2(0.90) |
|---|---|---|---|
| 新人B1（能力60） | 0.83 | **据置**（max()で素が勝つ） | 0.90へ上昇 |
| 中堅（能力100） | 0.76 | 0.82へ上昇 | 0.90へ上昇 |
| 円熟（能力144） | 0.53 | 0.82へ上昇 | 0.90へ上昇 |

⚠️**新人の段1が「据置」になるのは仕様として正しい**——新人の素の達成率は入賞30%で
既に本物の賭けであり、これ以上難しくする必要が無い。⚠️**「据置なのに払い戻しが出る」の
ではなく「素の分の悪さで賭けている」**と読む。

### ⚠️計測に忠実であるための注意（実装で変えてはいけない点）

- **`power`は味方（チームメイト）にも掛かる**（`newRider(power + tm.baseline, ...)`）。
  ⚠️較正はこの状態で測っているので、**「敵だけ強くする」に変えると較正が無効になる。**
  「レース全体の本気度が上がる」という読みで通す。気になるなら別弾で扱うこと。
- **`aiCap`も全体に掛ける**（較正プローブは`abilCap`をDIFFICULTIES行に置いて全体へ効かせた）。
- **プレイヤーの能力は生の値**（`effAbilities`で装備・バッジを乗せる前）。⚠️実プレイヤーは
  装備のぶん強いので、**実際の達成率は較正値よりやや高く出るはず**。実装後の再計測で確認する。
