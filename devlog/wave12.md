# 第12弾：アイテム・機材の拡充と経済圏の再設計（39番＋18番＋8番⑤の統合）

DEVLOG.md §43 の詳細。**39番（アイテム・機材の拡充とバランス／両モード）・18番（CP交換所の
拡充）・8番の保留⑤（資金の使い道の拡充）を統合**した弾。3つとも同じ経済圏で、別々に設計すると
価格帯とインフレ管理が破綻するため（統合の判断はDEVLOG §「次のアクション」39番に既述）。

## 着手前の実態調査（2026-08・Opusによる計測。設計の前提）

計測スクリプト：`scratchpad/w12_econ.mjs`・`w12_econ2.mjs`。

### ① シーズンは資金が構造的に余っている（最大の発見）

| | 金額 |
|---|---|
| 10年プレイの累計黒字 | **約 40,000万円** |
| 買い切りの総額 | **9,120万円**（パーツ16名分4,800＋設備4種×Lv5＝2,400＋内装4部屋＝1,920） |
| 選手獲得（スカウト/引き抜き） | 1人 84〜214万＝年に数名でも数百万規模 |

**使い道を全部足しても累計黒字の23%**。資金は2〜3年で意味を失う。
さらに**スタッフ・OBコーチは月給制で買い切りがゼロ**のため、資本を吸収する働きが構造的に無い
（Lv3×4種＋OBを雇っても年1,728万で、PRO期の年6,000万超の黒字を消せない）。

**同じ問題が過去に一度パッチされている**：`data/gear.js`の`ML_HOUSES`に
「稼いだ資金の使い道が尽きて余りがちだったため、終盤向けの最上位グレードを追加」（v20）という
コメントが残っている。**最上位を1段足す対症療法では同じことを繰り返す**ため、今回は構造から直す。

**初回試算の誤りと訂正**：当初シーズンの買い切りを「2,400万（設備のみ）」と見積もったが、
`PARTS`は**選手ごとに1個ずつ必要**（`partsInv`は所持数のカウンタ、`screens/season/hub/riders/
list.jsx`が選手別に装備）で、PRO16名フル装備だけで4,800万だった。結論（資金余剰）は不変。

### ② マイライフは真逆で、資金はむしろ足りない

| プレイの質（15年キャリア） | 累計収入 |
|---|---|
| 平凡（平均8位） | 2,592万 |
| 中堅（平均4位） | 5,976万 |
| エース（平均2位） | 14,178万 |

買い切りの総額は**9,660万**（現実的な最小構成）。ただし**その57%＝5,500万が才能開花系**
（成長力C→S 4,600＋成長タイプ変更900）で、これは第7弾（v43）で「450万で最強ビルド確定」の
抜け道を塞ぐために意図的に高くした部分＝**触ってはいけない**。
**それを除くと4,160万しかなく、中堅でも中盤で買い尽くす。**

### ③ `PARTS`は両モード共有（設計上の重要な制約）

`sim/race.js`に定義され、`controllers/season/shop.js`と`controllers/mylife/shop.js`の双方が
参照する。同じデータが担う役割が全く違う：
- **シーズン**：選手ごとに1個ずつ必要（12〜16名分）＝4,800万規模の反復的な出費
- **マイライフ**：プレイヤー1人分の1セットだけ＝300万で完結

**片方に都合よく作り替えると、もう片方が壊れる。**

### ④ 借金状態は既に機能している

`budget < 0`で全購入ガード（`s.budget < price`）が自然に効き、`chrome.jsx`が「（借金）」、
`race/status.jsx`が「返済まで買い物不可」を表示する。**年俸制で赤字に振れても受け皿は既にある。**

## 合意した設計（2026-08・`AskUserQuestion`で3点確認）

### 12-A：シーズンに選手の年俸制を導入（ユーザー判断・資金の出口の本丸）

現在の`UPKEEP_PER_RIDER = 3`（**誰でも一律**月3万）を、**能力に応じた年俸**へ置き換える。
狙いは、資金の出口が「チームの成長に自動で追従」すること。上限を1段足す対症療法（v20の
`ML_HOUSES`）と違い、買い切って終わりにならない。

#### 確定する式（`src/domain/season/salary.js` を新設）

```js
export const SALARY_BASE  = 40;  // OVR95相当での月額（万円）
export const SALARY_FLOOR = 45;  // これ以下は最低額
export const SALARY_SCALE = 50;
export const SALARY_EXP   = 2.6; // 上位ほど跳ねる非線形性

export function riderSalary(r) {                       // 万円/月
  const t = Math.max(0, overall(r) - SALARY_FLOOR) / SALARY_SCALE;
  return Math.max(1, Math.round(SALARY_BASE * Math.pow(t, SALARY_EXP)));
}
export function teamPayroll(roster) {
  return (roster || []).reduce((a, r) => a + riderSalary(r), 0);
}
```

**年齢係数は入れない（確定）**：加齢すると`overall`自体が衰えで下がるため、年齢を別途掛けると
二重計上になる。「ベテランは高い」を表現したいなら年齢ではなくOVRが既に担っている。

#### 較正結果（`scratchpad/w12_curve.mjs`・`w12_final.mjs`で3案を比較して確定）

| OVR | 55 | 65 | 70 | 75 | 80 | 85 | 88 | 90 | 95 | 100 |
|---|---|---|---|---|---|---|---|---|---|---|
| 月額 | 1 | 4 | 7 | 11 | 16 | 22 | 27 | 30 | 40 | 51 |

編成別の年間収支（原資＝年間収入−スタッフ等）：

| クラス | 編成 | 年俸 | 収支 |
|---|---|---|---|
| B1（原資1,483万） | 8名 OVR68 | 480万 | ＋1,003万 |
| B1 | 12名 OVR72（フル） | 1,152万 | ＋331万 |
| A（原資3,855万） | 10名 OVR80 | 1,920万 | ＋1,935万 |
| A | 14名 OVR84（フル） | 3,528万 | ＋327万 |
| PRO（原資7,382万） | 12名 OVR90 | 4,320万 | ＋3,062万 |
| PRO | 16名 OVR88（フル） | 5,184万 | ＋2,198万 |
| PRO | **16名 OVR95（全員スター）** | 7,680万 | **▲298万** |

**この較正の意図**：「フル編成そのもの」は罰しない（フルでも黒字＝育成の努力は報われる）。
罰するのは**全枠をスターで埋めること**だけ。10年累計の黒字は**約40,000万 → 約17,030万**に
下がり、買い切り総額9,120万＋移籍費と釣り合う水準になる。

**却下した案**：より急な設定（FLOOR=40/EXP=2.0）はPROフル編成が＋278万、B1フル編成が
▲821万となり、**B1でパーツ（8名分2,400万）が一生買えなくなる**ため却下。ゆるい設定
（BASE=34/FLOOR=48）は全編成が黒字で資金余剰が解決しないため却下。

#### 差し替える箇所（実質3つ・`UPKEEP_PER_RIDER`は削除）

| 場所 | 現在 | 変更後 |
|---|---|---|
| `controllers/season/month.js:311`（月次） | `roster.length * UPKEEP_PER_RIDER` | `teamPayroll(roster)` |
| `controllers/season/month.js:247`（年度末） | `survivors.length * UPKEEP_PER_RIDER` | `teamPayroll(survivors)` |
| `components/chrome.jsx:20`（表示） | `g.roster.length * UPKEEP_PER_RIDER` | `teamPayroll(g.roster)` |

#### 旧セーブ移行（確定）

既存セーブは一律月3万前提で編成されているため、そのまま適用するとPRO16名で月48万→432万と
**9倍**になり、いきなり借金状態に落ちる。以下で対処する：
- 保存項目に`payrollMigrated`（真偽値）を追加。
- `loadGame()`で`payrollMigrated`が未設定なら、**新方式の6ヶ月分**（`teamPayroll(roster)*6`）を
  一時金として`budget`へ加算し、フラグを立て、ログへ1行残す（文面はCLAUDE.md §7に従い
  「新しい年俸規定」等の内部用語を避けた平易な日本語にする）。
- 恒久的な二重コードパスは作らない（旧式計算は残さない）。一度きりの移行支援金で吸収する。

#### 確認済みの非影響

- `RELEGATE_LINE`・スポンサーのノルマは**ポイント**基準のため年俸制の影響を受けない。
- 借金状態の受け皿は既に機能している（`budget < 0`で全購入がガードされ、`chrome.jsx`が
  「（借金）」、`race/status.jsx`が「返済まで買い物不可」を表示する）。

### 12-B：マイライフのパーツを「育てる装備」へ（ユーザー判断）

**③の制約があるため、シーズンのパーツ体系には手を触れない。** マイライフ側にだけ
「プレイヤー自身の1台を育てる」レイヤーを足す。

**`partsInv`は所持数のカウンタで個体識別を持たない**（`{pid: 個数}`）ため、「所持している
特定の1個を強化する」形にはできない。**装備スロット単位で強化Lvを持つ**設計でこれを回避する。

#### 確定するデータと式

`src/data/gear.js` へ追加：
```js
export const ML_PART_UPGRADE_COST = [30, 55, 90, 150, 240]; // Lv0→1 … Lv4→5（万円）
export const ML_PART_LV_MAX = 5;
export const ML_PART_LV_MUL = 0.12;   // 1Lvあたり+12% → Lv5で1.6倍
```

`sim/race.js`の`effAbilities`（**パーツ効果を適用する唯一の箇所・61〜66行**）を変更：
```js
if (r.parts) {
  PART_SLOTS.forEach(slot => {
    const pid = r.parts[slot];
    if (!pid || !PARTS[pid]) return;
    const lv = (r.partLv && r.partLv[slot]) || 0;        // Seasonは常にundefined→0
    const mul = 1 + ML_PART_LV_MUL * lv;
    Object.entries(PARTS[pid].ab).forEach(([k, v]) => { e[k] += v * mul; });
  });
}
```
**シーズンは`partLv`を持たないので倍率1.0＝完全に従来どおり**（③の共有制約をこれで満たす）。

新規コントローラ `mlUpgradePart(s, slot)` を`controllers/mylife/shop.js`へ追加
（`mlBuyCar`/`mlBuyHouse`と同型の「即時適用の買い切り」）。

#### コストと効果の検算

- 1スロットをLv5まで＝**565万**、4スロット全部で**2,260万**。
- 効果：各スロット最上位を装備した状態の合計ボーナスは現在 平坦+10/登坂+10/スプ+12/スタ+10/独走+12
  （≒OVR+11相当）。Lv5で1.6倍になると ≒**OVR+17.6相当**＝**+6.6 OVRを2,260万で買う**。
- **妥当性**：才能開花系はA→Sだけで3,000万（成長力＝伸びしろの購入）。パーツ強化はそれより
  安く即効性がある代わりに上限が低い、という住み分けになる。
- これによりマイライフの才能開花系以外の買い切りは **4,160万 → 6,420万** となり、
  ②の「中堅（累計5,976万）でも中盤で買い尽くす」問題が解ける。

#### 旧セーブ互換

`player.partLv`は`ML_SAVE_FIELDS`の`"player"`に含まれて自動的に保存される（追加不要）。
旧セーブの`player`には存在しないため、**読み出しは必ず`(r.partLv && r.partLv[slot]) || 0`**
の形にして`undefined`を0として扱う（上記の式がそうなっている）。

### 12-C：CP交換所に新カテゴリ「解禁」を追加（ユーザー判断）

**実装順序の最後に置く。** 12-A・12-Bで両モードの資金バランスが大きく動き、既存CP特典
（「開幕資金+800万」等）の価値も同時に変わるため、**新バランスが固まってから較正する**
（この順序自体が設計上の要件）。

#### 既存との住み分け（調査済み）

- コース種別（`UNLOCK_TEMPLATES`）は**既に`totalEarnedCP`の累計で自動解禁**される仕組みが
  あり、消費しない。**ここと重複する品目は作らない。**
- 既存の`CP_SHOP`14項目（計875CP）は**すべて「開始時ブースト」**（初期資金・初期能力・
  デビュー特典）。新カテゴリは**「恒久的に上限そのものを解禁する」**軸にして差別化する。

#### 品目案（4件・計195CP／合計 875→1,070CP）

| 品目 | CP | 効果 | 12-A/Bとの噛み合い |
|---|---|---|---|
| スタッフ枠 +1 | 50 | `STAFF_MAX_BY_CLASS`[1,2,3]を全クラス+1 | 月給が増えるので年俸と資金を奪い合う |
| 所属枠 +2 | 45 | `ROSTER_MAX_BY_CLASS`[12,14,16]を+2 | **枠は増えるが年俸を払えるか**という葛藤になる |
| パーツ強化の上限 +2 | 40 | `ML_PART_LV_MAX` 5→7（Lv7で1.84倍） | 12-Bの伸びしろを延長 |
| 年俸交渉 −10% | 60 | `riderSalary()`の結果に×0.9 | 12-Aの緩和。CPで経済そのものを緩める上位特典 |

**最終確定は12-A/12-Bの実測後**：上表のCP価格は「強いマイライフ1キャリア≒100CP」を前提に
置いた暫定値で、年俸制導入後の資金の希少性が実測で分かってから最終決定する。

#### 配線上の注意（調査済み・ここが12-Cの実作業の大半）

`ROSTER_MAX_BY_CLASS`・`STAFF_MAX_BY_CLASS`は**定数を直接参照する箇所が8つある**
（`controllers/season/roster.js`×3・`transfer.js`・`shop.js`・`hooks/useSeasonGame.js`×2）。
しかも枠の判定は**購入のたびに実行時に**走るため、`initGame`で1回適用する既存perkの
やり方（`cpShopSeasonPerks()`）だけでは足りない。

**方針**：`initGame()`/`loadGame()`で`g.rosterMaxBonus`・`g.staffMaxBonus`をセーブ状態へ
書き込み（既存perkと同じ経路）、8箇所は
`ROSTER_MAX_BY_CLASS[cls] + (g.rosterMaxBonus || 0)` の形に統一する。
`loadMeta()`を判定のたびに呼ぶ形にはしない（実行時にlocalStorageを読むのは
これまで避けてきたイディオムに反する）。

## 実装順序

1. **12-A（年俸制）** — `domain/season/salary.js`を新設 → 3箇所を差し替え → `UPKEEP_PER_RIDER`
   を削除 → `loadGame()`へ移行支援金 → **検証1〜6を実行**。
2. **12-B（パーツ強化）** — `gear.js`へ3定数追加 → `effAbilities`にLv倍率 → `mlUpgradePart()`
   → 強化UI（`screens/mylife/events.jsx`のパーツ画面） → **検証7・8を実行**。
3. **12-C（CP新カテゴリ）** — 12-A/Bの実測値を見てCP価格を最終決定 → `CP_SHOP`へ4項目追加
   → 各効果の配線（`STAFF_MAX_BY_CLASS`等は定数直参照なので`cpShopSeasonPerks()`経由の
   加算に変える必要がある点に注意）。

## 検証計画（合否ラインを数値で固定する）

設計時の試算は`scratchpad/w12_econ.mjs`・`w12_curve.mjs`・`w12_final.mjs`。実装後は
**同じスクリプトを実コードの`riderSalary()`を読む形に差し替えて**再実行し、下表と突き合わせる。

| # | 検証項目 | 合否ライン |
|---|---|---|
| 1 | 年俸カーブが設計どおりか | OVR70=7万／80=16万／90=30万／95=40万（±1万） |
| 2 | 編成別の年間収支 | PRO16名OVR88＝**＋2,198万**／PRO16名OVR95＝**▲298万**（±10%） |
