# 第12弾：アイテム・機材の拡充と経済圏の再設計（39番＋18番＋8番⑤の統合）

DEVLOG.md §43 の詳細。**39番（アイテム・機材の拡充とバランス／両モード）・18番（CP交換所の
拡充）・8番の保留⑤（資金の使い道の拡充）を統合**した弾。3つとも同じ経済圏で、別々に設計すると
価格帯とインフレ管理が破綻するため（統合の判断はDEVLOG §「次のアクション」39番に既述）。

## 着手前の実態調査（2026-08・Opusによる計測。設計の前提）

計測スクリプト：`scratchpad/w12_econ.mjs`・`w12_econ2.mjs`。

### ① シーズンは資金が構造的に余っている（最大の発見）

| | 金額 |
|---|---|
| 10年プレイの累計黒字 | **約 40,000万円** |
| 買い切りの総額 | **9,120万円**（パーツ16名分4,800＋設備4種×Lv5＝2,400＋内装4部屋＝1,920） |
| 選手獲得（スカウト/引き抜き） | 1人 84〜214万＝年に数名でも数百万規模 |

**使い道を全部足しても累計黒字の23%**。資金は2〜3年で意味を失う。
さらに**スタッフ・OBコーチは月給制で買い切りがゼロ**のため、資本を吸収する働きが構造的に無い
（Lv3×4種＋OBを雇っても年1,728万で、PRO期の年6,000万超の黒字を消せない）。

**同じ問題が過去に一度パッチされている**：`data/gear.js`の`ML_HOUSES`に
「稼いだ資金の使い道が尽きて余りがちだったため、終盤向けの最上位グレードを追加」（v20）という
コメントが残っている。**最上位を1段足す対症療法では同じことを繰り返す**ため、今回は構造から直す。

**初回試算の誤りと訂正**：当初シーズンの買い切りを「2,400万（設備のみ）」と見積もったが、
`PARTS`は**選手ごとに1個ずつ必要**（`partsInv`は所持数のカウンタ、`screens/season/hub/riders/
list.jsx`が選手別に装備）で、PRO16名フル装備だけで4,800万だった。結論（資金余剰）は不変。

### ② マイライフは真逆で、資金はむしろ足りない

| プレイの質（15年キャリア） | 累計収入 |
|---|---|
| 平凡（平均8位） | 2,592万 |
| 中堅（平均4位） | 5,976万 |
| エース（平均2位） | 14,178万 |

買い切りの総額は**9,660万**（現実的な最小構成）。ただし**その57%＝5,500万が才能開花系**
（成長力C→S 4,600＋成長タイプ変更900）で、これは第7弾（v43）で「450万で最強ビルド確定」の
抜け道を塞ぐために意図的に高くした部分＝**触ってはいけない**。
**それを除くと4,160万しかなく、中堅でも中盤で買い尽くす。**

### ③ `PARTS`は両モード共有（設計上の重要な制約）

`sim/race.js`に定義され、`controllers/season/shop.js`と`controllers/mylife/shop.js`の双方が
参照する。同じデータが担う役割が全く違う：
- **シーズン**：選手ごとに1個ずつ必要（12〜16名分）＝4,800万規模の反復的な出費
- **マイライフ**：プレイヤー1人分の1セットだけ＝300万で完結

**片方に都合よく作り替えると、もう片方が壊れる。**

### ④ 借金状態は既に機能している

`budget < 0`で全購入ガード（`s.budget < price`）が自然に効き、`chrome.jsx`が「（借金）」、
`race/status.jsx`が「返済まで買い物不可」を表示する。**年俸制で赤字に振れても受け皿は既にある。**

## 合意した設計（2026-08・`AskUserQuestion`で3点確認）

### 12-A：シーズンに選手の年俸制を導入（ユーザー判断・資金の出口の本丸）

現在の`UPKEEP_PER_RIDER = 3`（**誰でも一律**月3万）を、**能力に応じた年俸**へ置き換える。
- **狙い**：資金の出口が「チームの成長に自動で追従」する。強い選手を集めるほど維持費が重くなり、
  「スターを何人抱えられるか」というチーム運営らしい葛藤が生まれる。上限を足す対症療法と違い、
  買い切ってしまえば終わり、にならない。
- **改修箇所はごく小さい**：`UPKEEP_PER_RIDER`の消費箇所は実質3つだけ
  （`controllers/season/month.js:247`＝年度末、`:311`＝月次、`components/chrome.jsx:20`＝表示）。
- **式の方針**：`riderSalary(rider)` を新規純関数として`domain/season/`に置き、OVRに対して
  非線形（上位ほど跳ねる）にする。年齢を掛けるかは実装時に実測して決める
  （若手は安く伸びしろ、ベテランは高いが即戦力、という綾を作れる）。
- **較正目標**：PRO期でチーム総年俸が年間収入の相当割合を占め、**16人フル編成だと赤字に振れる**
  水準。「全枠埋めるのが常に最適」を崩すのが目的。
- **要注意（実装時に必ず対応）**：
  - **旧セーブ移行**。既存セーブは一律月3万前提で編成されているため、年俸制を入れた瞬間に
    維持費が跳ね上がり、いきなり借金状態になり得る。移行時の緩和（初年度は据え置き等）か、
    そもそも旧セーブは旧式のまま計算するか、を決めること。
  - `RELEGATE_LINE`・スポンサーのノルマは**ポイント**基準なので年俸制の影響を受けない（確認済み）。
  - 年度末の`survivors.length * UPKEEP_PER_RIDER`（月次とは別経路）も同時に直すこと。

### 12-B：マイライフのパーツを「育てる装備」へ（ユーザー判断）

**③の制約があるため、シーズンのパーツ体系には手を触れない。** マイライフ側にだけ
「プレイヤー自身の1台を育てる」レイヤーを足す。
- `player.parts[slot]`（装備中のpid）はそのまま。**`player.partLv = { slot: lv }` を新設**し、
  資金を注いで強化するとその装備の`ab`にLv倍率が乗る。
- `effAbilities`（`sim/race.js:61-66`）がパーツ効果を適用する唯一の箇所なので、
  ここにLv倍率を掛けるだけで両モードに安全に対応できる（**シーズンは`partLv`を持たない＝
  倍率1.0で従来どおり**）。
- **`partsInv`は所持数のカウンタで個体識別を持たない**ため、「所持している特定の1個を強化する」
  形にはできない。**装備スロット単位で強化Lvを持つ**設計にすることでこの制約を回避する。
- これにより、才能開花系（5,500万・触れない）以外にも資金の行き先ができ、②の
  「4,160万で買い尽くす」問題が解ける。

### 12-C：CP交換所に新カテゴリを追加（ユーザー判断）

**実装順序の最後に置く。** 12-A・12-Bで両モードの資金バランスが大きく動くため、
既存CP特典（「開幕資金+800万」等）の価値も同時に変わる。**新バランスが固まってから
較正する**（この順序自体が設計上の要件）。
- 新カテゴリの候補：両モード共通の永続アンロック（コース種別・チームの解禁）、
  シーズンのスタッフ枠拡張、マイライフのパーツ強化Lv上限の解放など。
  **具体的な品目は12-A/12-Bの較正後に確定する。**

## 実装順序

1. **12-A（年俸制）** — 資金の出口の本丸。`riderSalary()`を新設し3箇所を差し替え、
   Node実測で年間収支を較正。旧セーブ移行方針もここで決める。
2. **12-B（パーツ強化）** — マイライフ側のみ。`partLv`新設＋`effAbilities`にLv倍率。
3. **12-C（CP新カテゴリ）** — 上2つの新バランスに対して較正してから品目を確定。

## 検証計画

1. **年俸制の前後で年間収支を実測**（PRO期の黒字が適正水準に収まるか。`w12_econ.mjs`を流用）。
2. **「何人まで抱えられるか」の境界を実測**（16人フルで赤字に振れるか、12人なら黒字か）。
3. **借金→回復のループが成立するか**（選手を放出して黒字化できるか＝詰みにならないか）。
4. マイライフのパーツ強化の費用対効果（才能開花系と比べて割に合うか）。
5. 旧セーブ互換（一律月3万前提の編成が、移行方針どおり破綻しないこと）。
6. 両モードのPlaywright回帰＋`npm run build`。

## スコープ外（今回やらないと決めたこと）

  モデルのまま据え置く）。
- **才能開花系の価格改定**（第7弾v43で抜け道封じのため意図的に高くした部分。触らない）。
- **収入側（賞金・スポンサー）の引き下げ**。12-Aの出口側で足りるかを実測してから判断する。
