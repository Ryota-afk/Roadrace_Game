# 第10弾：味方との協力の実感（#31）＋ assist作戦の是正

**状態**：完了（2026-08）。対象は#31＋§39から送られた`assist`作戦の是正。
A〜D・F・Gに加え、完了後の会話で見つかった「AI選手の能力値が毎レース再ロールされる」問題
（下記「追補」参照）も併せて解消した。

**発端**：「レース中に味方と協力できている実感がない。俯瞰カメラでもゴールスプリントでも、
僚友と協力している感触がまったく無い」。「俯瞰カメラのシミュレーションを変えてもいい」＝
**演出だけでなくシミュレーション本体に手を入れてよい**という許可をユーザーから得ている。
§39で`assist`作戦が全区分で数値的にも無意味だと判明したため、同じ弾で扱う。

## 調査で分かったこと

### 発見1（最重要）：sim上、味方が前で牽いても自分には何も起きない

**コードから直接読める事実であり、計測値に依存しない。** ドラフト中の選手は
`dist = groupDist`（＝牽引者のペース）で進み、消耗軽減`shelterMul = groupShelterMul(members.length)`は
**集団の人数だけ**、回復`regen = ENERGY_REGEN_BASE * backRatio`は**自分のslotだけ**で決まる。
つまり**前を牽いているのが味方か敵かで計算結果は1ビットも変わらない。**

味方依存の効果は実質3つしか存在しない：

| 効果 | 効く範囲 | 実体 |
|---|---|---|
| リードアウトのスリングショット | **最終区間のみ** | `slingshotAceIds` → `finishKick +0.045` |
| トレイン隊列の`slot`割り当て | 残り14%から（`progNow > 0.86`） | **見た目の位置だけ** |
| エースの`assistMul 0.78` | 全区間 | **出走前に静的に決まる**（動的な協力ではない） |

**「協力している実感がない」のは演出不足ではなく、実際に協力が存在しないから。**
これが#31の根本原因。

### 発見2：レースの7〜9割は、味方に何の表示も出ていない

実測：「味方が自分と同じ集団で牽引しているtick率」**8〜11%**、
「味方に展開タグ（トレイン/リードアウト/前待ち等）が付いているtick率」**27%**。
タグは設計上`frontZone = progNow > 0.72`／`trainZone = progNow > 0.86`以降しか出ないため、
序盤〜中盤は**構造的に無**。

### 発見3：「アシストに徹する」選手は、一度も牽かない

`canPull()`に`if (en.isAssisting) return false;`がある（v36の自滅対策）。
エースへの見返りは**出走前の能力値書き換え**で代替されているため、
レース中のアシストは実質「何もせず最後に流すだけ」。

なお**v36当時に無かった安全網が現在は存在する**：v38(#2)で`PULL_MIN_ENERGY=24`/
`PULL_RESUME_ENERGY=44`のヒステリシス（消耗したら牽引を降りて回復し、戻ったら復帰）が入った。
アシストは`role="sub"`・`committedBreak=false`なのでこのヒステリシスが効く。
**したがって除外を外しても自滅しない。**

### 発見4：エースへの「能力値書き換え」は作り話であり、構造的に上限がある

```js
const contrib = (playerTotal / 5 - 55) * 0.16 + (domestique ? 3〜5 : 0);
const boost = Math.max(2, Math.min(10, Math.round(contrib)));
const gap  = domestique ? (gold ? 4 : 6) : 9;
ace[k] = Math.min(99, Math.max((ace[k] || 0) + boost, (playerEff[k] || 0) - gap));
```

「アシストするとエースのステータスが魔法で上がる」という作り話であるうえ、
**`Math.min(99, ...)`のハードキャップ**と**下限が`playerEff - gap`止まり**のため、
能力を極めたプレイヤーほど「自分より弱い代役」に勝負を託す構造になる。

### 発見5：献身の報酬ゲートは「エースが3位以内」

`controllers/mylife/result.js:163` の `const success = ar <= 3;`。
ここを通らないと人気・評価・報酬（最大 人気+2.5／評価+4／+30万円）が一切出ず、
ログも「報われない走りになった」だけになる。**献身の体感はこのゲートの発火率がすべて。**

### 発見6：チーム順位悪化の主犯はassistではなく`chaseMode: "push"`の可能性

`assist`は`chaseMode: "push"`を持つ。同じpushを持つ`wait`単独でも能力85でチーム最上位が
悪化する傾向が出た。`push`は`rotSpan`を縮めて集団のローテを速める効果で、
献身の意味論には必須ではない。

### 訂正：計測ハーネスは正常だった

設計フェーズ終盤で`assist_split.mjs`と`assist_podium.mjs`が同じ条件のはずで食い違う数値
（能力105のエース平均順位が9.38 vs 4.22）を出し、一時「ハーネスが非決定論的」と疑い
このセクションに警告を書いた。**実装フェーズで検証した結果、誤りだった**：同一スクリプトを
2回実行して完全に一致することを確認済み（`assist_split.mjs`は決定論的）。真因は
2本のスクリプトの試行回数（`TRIALS`）が違っていたため、そもそも異なるレース集合を比較して
いただけだった（試行回数を揃えたら数値は近づいた）。**ハーネスの決定論化という作業は不要**。
較正は通常どおり、1本の計測スクリプトで進める。

## 合意した設計

ユーザー判断（2026-08）：
- 献身の対価＝**エースが本当に勝ち圏に入る**＋**レース外の見返りを厚くする**
  （「自分もそこそこ残る」は**選ばれなかった**＝自分の順位を捨てるのは設計意図どおり維持）
- エースへの能力値書き換え＝**廃止して実効果へ置換**
- 味方の風除け＝**AIチームにも対称に効かせる**

### A. チームドラフト（味方の風除け）を新設 ← 弾の核

同じ集団で自分より前にいる味方の人数と、味方が牽引中かどうかに応じて、
ドラフト中の消耗を軽減する。**全チームに対称に適用する。**

- 現状の協力効果は「静的（出走前）」か「終端（最終区間）」しかなく、**連続的なものが1つも無い**。
  これを入れて初めて「味方が前を固めてくれている間は脚が減らない」が数値として成立する。
- **脚バーの減り方としてそのまま画面に出る**ので、説明文を足さずに伝わる（CLAUDE.md §7に沿う）。
- 実装位置：`simulateTicks`のドラフト分岐、`shelterMul`/`regen`を計算している箇所。
- 新定数（要較正）：1人あたりの軽減量／牽引中ボーナス／軽減の下限（大人数チームの暴走止め）。
- リスク：AIチームも強くなるので難易度が上がる。`bracket_sweep.mjs`で
  balanced時のプレイヤー勝率が落ちすぎていないか確認し、必要なら下限で抑える。

### B. アシストが「実際に牽く」役へ戻る

`canPull()`の`isAssisting`除外を外す。自滅は既存の`assistMul 0.78`＋
発見3のヒステリシスで抑える。これでアシストはAの風除けを**供給する側**になる。

### C. エースへの能力値書き換えを廃止し、Aの実効果へ置換

`AB_KEYS.forEach(k => { ace[k] = ... })`と`ace.assistBoost`を削除。
`ace.isAssisting = true`も削除する（`canPull`はエースを既に除外、
最終区間の流しは`!en.isAce`ガード済み、リードアウト候補も除外済みなので、
実質`assistMul 0.78`だけが効いており、それこそがAで置換すべきもの）。

**互換性の確認済み**：`sim.assistedAce`は`{id, name, rank, boost}`だが、
`result.js`が使うのは`id`/`name`/`rank`のみで`boost`は未使用。**削除して安全。**

### D. `assist`から`chaseMode: "push"`を外す（→`"normal"`）

実測で純マイナスの疑いが強く、献身の意味論にも必須ではない。

### E. 最終区間の流し（`groupDist * 0.90`）は維持

ユーザーが「自分もそこそこ残る」を選ばなかったため、自分の順位を捨てる設計は維持する。

### F. レース外の見返りを厚くする

`result.js`の献身報酬（人気/評価/資金）を引き上げる。現状は`ar <= 3`でのみ発火し、
外れると完全にゼロ。**外れた時にも最低限の見返りを置く**か、
成功時の額を上げるかは実装フェーズで決める（献身の道＝`devotion`アンビションへの
カウントは既に確実に入る作りになっている）。

### G. 見せ方（A〜Fが入って初めて意味が出る）

- 風除けを供給している選手に新しい展開タグ（例：`shelter`）を立て、既存の`tagHist`→
  バッジ機構にそのまま流す（＝RaceView側は表の1行追加で済む）。
- タグを終盤限定にせず、**味方が実際に風除けしている間ずっと**出す。
  これで発見2の「7〜9割が無表示」が解消する。

## 実装フェーズでの発見：E案（能力書き換え廃止）の前提が崩れていた

**実装済み**（`src/sim/race.js`・`src/state/state.js`・`src/controllers/mylife/result.js`・
`src/components/RaceView.jsx`）：
- A：チームドラフト。同集団内の味方の人数・牽引者が味方かで`keepThresh`（ついていける基準、
  `TEAM_KEEP_RELIEF_*`）と消耗（`teamShelterMul`、`TEAM_SHELTER_*`）を対称に緩和。
- B：`canPull()`から`isAssisting`除外を撤去。アシストが実際に牽けるようになった。
- C：エースへの能力値書き換え（`ace[k]=...`・`assistBoost`・`ace.isAssisting=true`）を全廃。
- D：`assist`から`chaseMode: "push"`を撤去（`"normal"`へ）。
- F：`result.js`の献身報酬を2段階化（表彰台＝手厚く、10位以内＝小さな見返り）。
- G：風除けを受けている選手に`tag: "shelter"`（表示は「援護中」）を新設。

**測定で判明した問題**：正しい対照（同レース内で「支援したエース」と「支援を受けていない
他のチームメイト」を比較）では、チームドラフトは機能している——支援したエースは同程度の
地力の無支援チームメイトより明確に良い順位で終わる（例：能力85で平均順位15.24 vs 20.54、
能力105で13.95 vs 21.38）。

**しかし「エースが表彰台に入るか」で見ると、能力値書き換えを廃止したことで激減した**ように
最初は見えた（能力85: 12%→0%、能力93: 52%→9%、能力105: 50%→5%）。

### 訂正：計測が実ゲームと違うコードパスを踏んでいた

上記の計測は`buildMyLifeSim`の`teammates`引数に`null`を渡していたため、実際のマイライフが
使う「固定チームメイト」分岐（`isMyTeam && teammates`・`newRider(power+4, ...)`・**cap94**）
ではなく、`worldRosters`分岐（永続ロースター基準・**cap96**、対戦相手にも及ぶ強い個体差）に
フォールバックしていた。ユーザーからの「エースを毎回別に生成するのは固定チームメイトの原則に
反しないか」という指摘をきっかけに、`mlGenTeammates()`で実際に固定メンバーを作り
正しいコードパスで測り直した結果、**能力値書き換え無しでも十分に機能している**と判明：

| 能力(プレイヤー) | assist: 支援したエースの表彰台率 | assist: チーム表彰台率 | balanced: チーム表彰台率 |
|---|---|---|---|
| 85（格下） | 28% | **45%** | 4% |
| 105（格上） | 38% | 36% | 68〜70% |

格下プレイヤーでは献身がチーム表彰台率を4%→45%に押し上げる（＝自分では勝てなくても
チームとしては勝負できる、という献身本来の価値）。格上プレイヤーでは献身がbalanced/waitより
低くなる（＝自分が最強の手駒なのに手放すのは相応の代償、という整合的なバランス）。
**能力値書き換えの復活・エースの別枠強生成（案②③）は不要と判断し、E案のまま確定する。**

## 追補：AI選手の能力値が毎レース再ロールされていた問題（2026-08）

**発端**：ユーザーから「固定チームメイトの能力値って毎回変わってたの？」という質問。

**調査結果（4パターンに分かれていた）**：
- マイライフの自分のチームメイト・ライバル：身分は固定だが、**能力値は毎レース非決定論的な
  `rng`（`Date.now()`基準）で再ロールされていた**（実装漏れ）。
- 対戦AIの永続ロースター（マイライフ・シーズン共通）：`id+年`でシード済み＝**既に年内固定**。
  設計コメントにも明記されていた（「stats はid＋yearでシードして年内は安定」）。
- シーズンの自分のロースター：そもそも再生成しない（実データを保持・成長で変化）。
- 殿堂入りの過去選手：引退時のスナップショットを固定の減衰式で反映（再ロールなし）。

つまり「対戦AIの永続ロースター」は既にご要望どおりだったが、**自分のチームメイトとライバルだけ
この設計から取り残されていた**。

**ユーザーからの追加指摘**：「年内完全に同じ能力だと急成長選手みたいなのがいなくて寂しくないか」。
調査の結果、AI選手の「毎回の当たり外れ」を担っていたのは実質この乱雑な再ロールだけで、
プレイヤー専用の`form`（ピーキング）はAI選手には常に無効（`formMul`が1.0固定）だった。
土台を固定するだけでは「絶好調の一週間」のような表情が消えてしまう。

**実装した設計**：
1. **土台をid+年でシード**——`core/core.js`に`idYearSeed(id, year)`を新設し、
   世界ロースターが個別に書いていた式を集約。マイライフの自チームメイト・ライバル・好敵手の
   ロールをこれに差し替え（世界ロースター・弟子は元々このパターンだったので変更なし）。
2. **AI選手にも控えめなform（当日の調子）を追加**——`core/core.js`に`aiFormRoll(rng)`を新設
   （±5%程度、プレイヤー本人のピーキング±17%より小さい）。既存の`effAbilities()`の`formMul`を
   そのまま流用するだけで新しい仕組みは足していない。土台の固定と対になる形で、
   `state.js`（マイライフ）・`logic/support.js`（シーズン）双方のAI選手生成（`members.map()`の
   `effAbilities`呼び出し直前）に適用。プレイヤー自身の`squad`・player本人には適用しない。

**検証**：同じ年に5回レースを建て直し、チームメイト1人目の身分（id・名前）と実効能力を比較
（`scratchpad/stability_check.mjs`）。実効能力は81.5〜86.3（±3%程度、formの揺れのみ）で
安定し、翌年は92.66へ明確にジャンプ（`power`上昇＋世代の自然な変化）。狙いどおり
「年内は同じ人物として安定・年をまたぐと自然に変化・毎回小さな当たり外れがある」になった。
マイライフ複数年回帰（年11まで）・シーズン判断カードの両方でエラー無しを確認。
