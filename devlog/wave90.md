# 第90弾：第89弾で見つかった3件の是正（設計）

**状態**：**①②③とも結論確定（②は「上限を下げない」で決着）。実装は未着手。**

第89弾の実測で判明した3件を直す。

## ① 人気度の逓減を、素通りしていた4経路にも適用（確定）

### 現状

第87弾で `domain/mylife/popularity.js` の `applyPopGain` に逓減 `× (1 - 現在値/100)` を
入れたが、⚠️**人気度を直接書き換える経路が他に4つあり、そこは素通りしていた**。
結果、第89弾の実測では⚠️**毎年4〜6ヶ月で100に到達し、年の半分以上を張り付いて過ごす**。

| 場所 | 内容 | 値 |
|---|---|---|
| `controllers/mylife/event.js:30` | イベントの`popularityDelta` | +2〜+8、⚠️**および −4／−6** |
| `controllers/mylife/event.js:157` | ライバル会話シーンの応答 | +3 |
| `controllers/mylife/result.js:191` | アシスト成功の`assistPop` | +0.5〜+3 |
| `domain/mylife/ambition.js:31` | アンビション報酬の`reward.pop` | ⚠️**+6〜+25** |

### ⚠️設計上の注意：逓減は「増加時のみ」

⚠️**`popularityDelta` には負の値が実在する**（`data/events.js` に −6 と −4 が1件ずつ）。
`(1 - 現在値/100)` を負の値に掛けると⚠️**人気が高いほどスキャンダルの打撃が小さくなる**という
逆転が起きる。⚠️**逓減は増加時にだけ適用すること。**

### 変更

`domain/mylife/popularity.js` に、加算だけを行う小さな純関数を追加して4箇所から共有する
（`applyPopGain`は`POP_MILESTONES`の判定も行うため、そのままでは流用できない）：

```js
// 人気度の増減を1箇所に集約する。増加にだけ逓減を掛ける（減少は減衰させない——
// 人気が高いほどスキャンダルの打撃が小さくなるのは逆）。
export function popAdd(cur, delta) {
  const eff = delta > 0 ? delta * (1 - (cur || 0) / 100) : delta;
  return Math.max(0, Math.min(100, (cur || 0) + eff));
}
```

`applyPopGain` の内部もこの関数を使う形へ統一する（⚠️**逓減の式が2箇所に散らないように**）。

4箇所の書き換えはいずれも同じ形：
```js
player.popularity = popAdd(player.popularity, <delta>);
```

⚠️**`POP_MILESTONES`の到達判定は今回いじらない。** 現状はレース由来の増加でしか
判定されないが、それを変えると到達ボーナス（80〜400万円）の入り方が変わり別の
バランス変更になる。⚠️**「次のアクション」へ上げる。**

## ② 年俸のクラス別上限 → ⚠️**下げない（実測で決着）**

第89弾は「10年目の資金7,507万＝最高額の買い物900万の8.3倍で目標未達」と結論したが、
⚠️**その計測はシンク（第88弾の2プロジェクト）を一度も使っていない**。

`scratchpad/w90_income.mjs` で収支能力を突き合わせた：

| | 金額 |
|---|---|
| 10年目の収入（実測） | **1,448万/年** |
| ワンオフ機材を常時回す（最短3ヶ月・初期費用のみ） | 1,600万/年 |
| 科学トレーニングを常時回す（最短4ヶ月・初期費用のみ） | 1,500万/年 |
| **2つの合計（追加投資なしの最小）** | **3,100万/年＝収入の2.1倍** |

⚠️**シンクの吸収力は収入の2倍以上あり、追加投資を使えば上限が無い。**
つまり資金問題は第88弾で既に解決しており、⚠️**第89弾の数字は「シンクを一切使わない
最悪ケース」を見ていただけ**の可能性が高い。

⚠️**この状態で上限を下げると、問題が無い序盤を無用に苦しくするだけになる。**
結論を出す前に、シンクを実際に使う自動プレイ（`w91_play.mjs`）で実測した。

### ⚠️実測結果：シンクが収入を完全に吸収していた → **上限は下げない**

`w91_play.mjs`＝第89弾のハーネスに「2ヶ月に一度ショップへ寄り、開始・追加投資・完成の
ボタンを押す」挙動を足したもの。⚠️**押せる中で常に最大額を選ぶ**（+500万／+800万を優先）
ため、これは**「使えるだけ使う」極端側**の計測である。

| 年目 | 資金（シンク未使用・第89弾） | 資金（シンク使用・今回） |
|---|---|---|
| 5 | 1,353万 | **50万** |
| 10 | **7,507万** | **55万** |
| 20 | 33,148万 | **91万** |
| 37 | 約70,000万 | **518万** |

⚠️**資金は37年間ずっと50〜500万円で平坦**（シンク操作282回、エラー0件）。
⚠️**「使わない＝7,507万」と「使い切る＝55万」の間にプレイヤーの選択が生まれており、
これはシンクとして機能しているということ。**

⚠️**結論：`ML_SALARY_CAP`は下げない。** 第89弾の「10年目で目標未達」は
**シンクを使わない極端側だけを見た誤った結論**だった。上限を下げれば、
シンクを使うプレイヤーは常時破産寸前になる（実測でも11年目に資金3万まで落ちている）。

⚠️**副次的な観察**：資金が常時ゼロ近辺で推移するため、⚠️**赤字ペナルティ
（`debtMonths`・3段階で強制売却）に触れる危険がある。** 今回の実測ではマイナスに
落ちなかった（資金不足だとプロジェクトを開始できず自然に止まるため）が、
⚠️**「シンクに注ぎ込んだ結果として破産する」経路が成立しないかは別途確認が要る**——
「次のアクション」へ上げる。

## ③ 移籍時の年俸にクラス上限を再適用（確定）

`controllers/mylife/career.js:39`：

```js
const salary = Math.round(s.salary * offer.salaryMul);   // ⚠️上限の再適用が無い
```

第87弾で年度末の改定にはクラス別上限を入れたが、⚠️**移籍の年俸倍率（1.05〜1.6）には
入れ忘れていた**。実測で**クラス0（B1・上限1,200万）なのに年俸3,300万**が繰り返し観測される。

### 変更

```js
const salary = Math.min(
  ML_SALARY_CAP[classIdx],
  Math.round(s.salary * offer.salaryMul)
);
```

⚠️**`classIdx` は同じ関数内で `offer.tier` から先に確定させること**（移籍先のクラスの上限を
使う。現行コードは`salary`を`classIdx`より前で計算しているので、順序の入れ替えが要る）。

⚠️**下限（`ML_SALARY_FLOOR`）は掛けない。** 移籍は上振れの機会であり、
下限で底上げする場面ではない（年度末の改定とは意味が違う）。

## ⚠️この弾で得た教訓

⚠️**「1箇所に集約したから安全」と書いたら、その"1箇所"が本当に全経路の合流点か数える。**
第84弾で`applyPopGain`を切り出したとき「通常レースとチームTTの両方が通る唯一の合流点」と
記録したが、⚠️**それは"レース由来の"人気度に限った話**で、イベント・アシスト・アンビションの
3系統を見ていなかった。第83弾・第85弾で同じ類型（同じ値が複数箇所・片方だけ直す）を
記録した本人が3回目を踏んだ。

⚠️**対策**：値の書き込み箇所は`grep -rn "<フィールド名>" src/ | grep "="`で**必ず全部数えてから**
「集約した」と書く。
