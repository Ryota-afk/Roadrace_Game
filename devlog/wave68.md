# 第68弾：遷移アニメーションの強さ調整

**状態**：**実装・検証完了（2026-08）。**

## 発端：「アニメーションが動いていない」

第67弾までで両モードに遷移アニメーションを入れたが、ユーザーがiPadで実プレイしたところ
「アニメーション遷移が実装されていない気がする」との報告。

### ⚠️私が最初に立てた仮説は外れており、決めつけを指摘された

最初に「配信物が古い（キャッシュ）のでは」と推測して判別マーカーを提示したが、ユーザーは
**新ビルドを見ており、かつ「弱い」のではなく「動いていない」**と明言。
⚠️**「決めつけないで」との指摘を受けた。** 実測せずに原因を断定するのは、この弾で2度
繰り返した失敗パターン（1度目は配信の話、2度目はこの推測）。

### 実測できない制約と、その回避

原因を確定させるにはWebKit（iPad Safari）での実測が要るが、
⚠️**PlaywrightのWebKitはこの環境のネットワークポリシーでダウンロードが拒否される**
（`playwright.download.prss.microsoft.com`が403）。手元にあるのはChromiumのみ。

そこで**実機側で走らせる診断ページ**をArtifactとして作り、ユーザーに開いてもらう形にした。
測定項目は5つ：

1. `prefers-reduced-motion` の状態
2. ⚠️**ゲーム本体のCSSがその端末で実際に何msへ解決されるか**（`transitions.css`の実物を
   診断ページに持ち込み、`getComputedStyle().animationDuration`を読む）＝決定打
3. CSSアニメーションが発火するか（`getAnimations()`）
4. `transform: none` を終点にした補間が効くか（`currentTime`を中間に固定して実測）
5. `clip-path: inset()` のアニメーション対応

⚠️診断ページ自体をChromiumで`reducedMotion: "reduce"` / `"no-preference"`の両方で
実行し、判定が正しく切り替わることを検証してから渡した（reduce時に`0.01s`を検出してNG、
通常時は`0.18s`でOK）。

### 原因：iPadOSの「視差効果を減らす」

ユーザーの回答は**「原因はそれでした」**。iPadOS の
**設定 → アクセシビリティ → 動作 → 視差効果を減らす** がONだったため、第66弾で入れた
安全策が働いていた。

```css
@media (prefers-reduced-motion: reduce) {
  .ml-enter-* { animation-duration: .01s !important; }
}
```

⚠️**バグではなく仕様どおりの動作**。ただし体感は「弱い」ではなく完全な「動かない」に
なるため、⚠️**今後「アニメーションが動かない」という報告を受けたら、コードを疑う前に
まずこの設定を確認すること。**

## 強さの調整（案B採用）

設定を切った後、ユーザーから「でも、動きは弱いかも」との指摘。
CLAUDE.md §8の手順（いきなり実装せず、複数候補を実際に見える形で提示→選択→合意→実装）
に従い、**実機で触って比べられる比較Artifact**を作成した。

### なぜ静止画やテキストでは駄目だったか

動きの強さは静止画で判断できない。§8が挙げる「テキストモック／HTML／スクリーンショット等」
のうち、この題材で唯一機能するのは**触れるHTML**だった。比較ページは：

- 現行／案A／案B／案Cを切り替えるセレクタ
- ゲームの実画面と同じ中身（実データ・実文言。§8の「モックはプレースホルダーを使わない」）
- タブを何度でも押し直せる（動きは1度では判断できない）
- 「一覧が満ちる」「レースへ進む」「翌月へ進む」も個別に試せる

⚠️**イージングは4案とも同一**にした。距離と長さの2軸だけを動かし、比較の軸をぶらさない。

### 候補と採用値

| 項目 | 現行 | 案A | **案B（採用）** | 案C |
|---|---|---|---|---|
| タブの移動距離 | 24px | 36px | **56px** | 80px |
| タブの長さ | .2s | .26s | **.32s** | .38s |
| 持ち上がり距離 | 7px | 14px | **22px** | 32px |
| 持ち上がり長さ | .18s | .24s | **.28s** | .34s |
| 一覧が満ちる | .3s | .38s | **.45s** | .55s |
| レースへ進む | 52px | 72px | **100px** | 140px |

⚠️**弱さの主因は「持ち上がり（rise）の7px」だったと見ている。** これは画面を開いたときの
既定の動きで、タブ移動以外のほぼ全画面がこれに当たる。7pxは知覚しづらく、
タブ移動の24pxだけが見えていたため「タブは動くが他は動かない」と感じられていた可能性が高い。

`ml-year-pulse`（月送り時のヘッダー）も`.3s`→`.45s`へ揃えた（本文の`ml-enter-month`と
同じ長さで動くべきもののため）。

## 変更したファイル

`src/styles/transitions.css` のみ。⚠️**数値だけを変更し、イージング・分類ロジック
（どの画面がどの動きになるか）・`prefers-reduced-motion`の扱いには触れていない。**

## 検証

- タブ遷移が実測`320ms`（案Bの`.32s`）で発火することをPlaywrightで確認
- `npm run build`成功。⚠️配信物`index.html`にも新しい値（`56px`/`22px`/`100px`）が
  含まれることをgrepで確認
- 既存回帰（`w66_sweep.mjs`＝マイライフ全タブ＋世界／記録配下）で`pageerror`ゼロ
- `master`へマージ・push済み

## この弾で得た教訓

1. ⚠️**「動かない」報告を受けたら、まず`prefers-reduced-motion`を確認する。**
   コードを疑うのはその後。
2. ⚠️**実測できない環境（WebKit不在）では、実機側で走る診断を作って渡す。**
   推測で原因を断定しない。診断ページ自体も、渡す前に両分岐で検証する。
3. ⚠️**動きの設計は、触れるものを作って選んでもらう。** 静止画では判断できない。
