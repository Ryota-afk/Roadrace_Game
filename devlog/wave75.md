# ⚠️原因A：逃げ役の割り当てが脚質と相関し、逃げ役は必ず沈む

## 発見

`sim/ticks.js:185` `assignAIRoles`：

```js
const peak = Math.max(r.flat, r.climb, r.sprint, r.stamina, r.solo);
const sprintGap = peak - r.sprint;
const breakawayChance = Math.min(0.65, 0.06 + sprintGap * 0.022);
```

実際の`newRider`出力から算出した脚質ごとの逃げ役確率（n=500）：

| 脚質 | 平均sprintGap | 逃げ役になる確率 | 山岳ロードの10位以内倍率 |
|---|---|---|---|
| SPR | 0.4 | **6.9%** | ×1.46 |
| PUN | 4.4 | **15.7%** | ×1.89 |
| CLM | 23.2 | **53.1%** | ×0.45 |
| TT | 15.3 | 39.2% | ×0.67 |
| RUL | 15.1 | 38.7% | ×0.60 |

⚠️**逃げ役確率と不利さの相関係数 −0.899。**

## 因果の確認（相関で終わらせない）

役割別の着順を直接集計した（`scratchpad/w75_role.mjs`・クリテリウム）：

| 役割 | 人数 | 平均着順 | 10位以内率 |
|---|---|---|---|
| flat（平坦アシスト） | 302 | **12.1位** | 54.6% |
| ace | 320 | 16.6位 | 33.8% |
| sub | 309 | 17.6位 | 20.7% |
| **breakaway（逃げ役）** | 328 | **25.3位** | **10.4%** |
| mountain（山岳アシスト） | 82 | 26.4位 | 4.9% |

脚質ごとの役割の内訳（クリテリウム）：
**SPR**＝flat 69%／逃げ役 **4%**、**CLM**＝**逃げ役 45%**／mountain 30%。

⚠️**逃げ役は平均25位で沈む役割であり、クライマーはそこに45%の確率で自動的に放り込まれる。**

## ⚠️なぜこれが見過ごされてきたか

式のコメントは「スプリントが弱点→集団ゴールで不利→早逃げに出やすい」と書いており、
**発想としては現実のロードレースに忠実**である。問題は組み合わせのほう——

⚠️**DEVLOG §88〜89で「逃げの数値を追う仕事はもう再開しない」と打ち切っている**
（第52〜59弾で7回挑戦し、効いたのは1回だけ）。逃げが構造的に不利なことは既知で、
対処を諦めた領域である。**その勝てないと分かっている戦術に、特定の脚質だけが
自動で送り込まれ続けていた。** 「逃げが弱い」問題と「役割割り当てが脚質に偏っている」
問題を別々に扱っていたため、掛け算になっていることに誰も気付かなかった。

⚠️**重要な区別**：ここを直すのは「逃げを強くする」ことではなく「勝てない戦術への
送り込みを脚質で偏らせない」ことなので、§88〜89の禁止事項（逃げの速度・持続を追う）には
抵触しない。

# ⚠️原因B：得意地形で強いほど集団の前方に置かれ、回復を受けられず自滅する

## 発見

原因Aで説明できるのはAI側だけ。⚠️**プレイヤーは逃げ役に自動割り当てされない**
（tacticで選ぶ）ので、別の原因があるはずだと考えて切り分けた（`scratchpad/w75_player.mjs`）。

山岳ロード・プレイヤーはエース（n=50）：

| 条件 | 平均着順 | 勝者との差 | 10位以内 |
|---|---|---|---|
| CLMそのまま (climb86 sprint63 accel44) | 24.9位 | 129秒 | 4% |
| sprintだけ85に（climbは86のまま） | 19.6位 | 112秒 | 34% |
| **typeラベルだけSPRに（能力はCLMのまま）** | **26.3位** | 126秒 | 4% |
| **能力をSPR型に置換（typeはCLMのまま）** | **9.1位** | **41秒** | **74%** |

⚠️**typeラベルは無関係で、能力の形が全てを決めている。** そして
⚠️**山岳コースなのに`climb`を86→63に下げたほうが10位分速い**という転倒が残った。

## ⚠️外した仮説2つ（記録して繰り返さない）

`segmentAbility`・`finishAbility`の式では説明できなかったため、tick単位で観測した。
⚠️**その過程で仮説を2回外している。同じ道を辿らないために両方残す。**

- ⚠️**外れ①「登坂が速いと集団より前へ出てしまい単独走(solo)になる」**——`solo`のtick比率は
  climb 63/86/110 で 3.6%→12.2%→14.6% と確かに増えるが、⚠️**`solo`のtickの82〜93%は
  「前に他の選手がいる」＝後方**だった（`scratchpad/w75_solo_why.mjs`）。コードを正確に読むと
  `ticks.js:553`の判定は`ownCapable >= groupDist * keepThresh`で、**`solo`は「遅すぎて千切れた」
  状態**であって「速すぎて抜け出した」ではない（コメントにも「千切れて単独走になった選手」とある）。
- ⚠️**外れ②「前方の小集団に残り`groupShelterMul`の風除けを失う」**——所属集団の人数を測ると
  25%/50%/70%地点で**3条件ともほぼ同一**（50%地点で27.3／27.8／28.1人）だった

## ⚠️機構の確定：計装した複製srcで消耗と回復を分解した

`src`を`scratchpad/w75src`へ複製し、`energyDrain`の適用箇所に計装を入れて内訳を直接測った
（`scratchpad/w75_acct.mjs`／`w75_acct2.mjs`）。⚠️**`solo`は「千切れた結果」でもあり
原因と結果が循環するため、集団内(`draft`)にいる間のtickだけに限定して切り分けた。**

**山岳ロード・集団内にいる間だけの1tickあたり収支（n=20レース）：**

| プレイヤーの`climb` | 消耗 | **回復** | **差引** | 集団内の平均位置 |
|---|---|---|---|---|
| 63 | 0.1740 | 0.1757 | **−0.0017（収支ゼロ）** | 35.6%（0%＝先頭） |
| 86 | 0.1764 | 0.1411 | **+0.0353** | 29.5% |
| 110 | 0.1781 | **0.1273** | **+0.0508** | 26.9% |

⚠️**消耗はほぼ同じ（+2.4%）。回復だけが28%減っている。** 1レースあたり約1,600 draft tickなので、
climb 110 は**1レースで約82ポイントのエネルギー赤字**（初期値100）。climb 63 は収支ゼロで走り切れる。

## 原因の所在（コード）

`ticks.js:503-508`——**集団内の位置(`slot`)が「その区間での強さ」順に決まる**：

```js
const frontStrength = (c) => c.ownCapable / groupDist - (conserve...) + (holdOn...);
ranked.sort((a, b) => frontStrength(b) - frontStrength(a));
ranked.forEach(c => { c.en.slot = nextSlot++; });   // 強い順に前から詰める
```

そして`ticks.js:616-618`——**回復は集団内の位置だけで決まる**：

```js
const backRatio = sheltered ? Math.min(1, (en.slot || 0) / totalDraft) : 0;
const regen = sheltered ? ENERGY_REGEN_BASE * backRatio * (windActive ? 0.5 : 1) : 0;
```

⚠️**その区間で強い選手ほど前に置かれ、前に置かれた選手は回復をほぼ受け取れない。**
弱い選手は後方で回復しながら生き延び、強い選手は前で削られて枯れる。

そこから先は連鎖する：エネルギーが減る→`energyPenaltyMul`で速度が落ちる→
`ownCapable`が`groupDist * keepThresh`を割る→千切れて`solo`→
`solo`は`effortCost`1.3かつ風除け無し（`shelterMul`が0.55→1.0）で**約2.8倍の消耗**→さらに沈む。
⚠️**`solo`の激増（drainの13%→46%）は原因ではなく、この連鎖の結果である。**

## ⚠️この原因が意味すること

**得意な地形で、得意な能力が高いほど自滅する。**
これは本作の根幹——DEVLOGの「育成の方向転換」に明記された
**「能力値で個性を出すのをやめ、バッジで個性を出す」**、そして脚質そのものの存在意義——と
正面から矛盾する。⚠️**育てるほど不利になる。**

⚠️**脚質ごとの有利不利も、これで完全に説明できる**——「その地形で一番強い者が損をする」ので、
山岳ではCLMが（climb 86で突出）、平坦ではRULが（flat 85で突出）前に置かれて損をする。
⚠️**PUNが全コースで最強（×1.89〜2.01）なのは、climb 79／sprint 79／flat 72と
「どの地形でも2番手」で、一度も先頭に置かれないから**である。第74弾-Cで
「`climb`を110に上げるとむしろ悪化」という不可解な観測を残していたが、その正体がこれだった。

# 修正の方向（設計判断が要るため未着手）

## 原因Aの候補

⚠️**`sprintGap`は2箇所で使われている。片方だけ直しても、もう片方が同じ偏りを再生産する。**
- `ticks.js:185` `assignAIRoles`＝レース開始時の役割割り当て
- `ticks.js:309` 終盤の自然発生アタック（`sprintGap < 8`で足切りし、`sprintGap`で確率が上がる）

実測（クリテリウム）：**一度でもattackに入った率はCLM 72%／TT 66%／RUL 58%に対しSPRは5%。**

- **A-1. 脚質依存を撤廃**——`breakawayChance`を全脚質一律（例12%）に。最も単純。
- **A-2. 依存を弱める**——係数`0.022`を下げ、上限`0.65`も下げる。現実味を残す。
- **A-3. 別の軸で選ぶ**——チーム内の序列（エースになれない選手ほど逃げる）等。

## 原因Bの候補（⚠️機構の再特定に伴い書き直した）

核心は**「slotが地形での強さ順」×「regenがslotだけで決まる」**の組み合わせ。

- **B-1. 回復を位置だけに依存させない**——`regen = ENERGY_REGEN_BASE * backRatio`の傾斜を緩め、
  先頭でも最低限は回復する形にする（例：`(0.35 + 0.65 * backRatio)`）。⚠️**最小の変更で
  収支の符号を直接動かせる。** 副作用：集団全体が持つので千切れが減り、決着が団子になり得る。
- **B-2. エース／温存中の選手を前に置かない**——`frontStrength`に`isAce`の後方バイアスを足す
  （現実の「エースは終盤まで風除けの中に隠れる」）。⚠️既に`conserveLeft`／`holdOn`のバイアスと、
  トレイン時の`ace.slot = helpers.length`という前例がある＝設計思想としては既存路線の延長。
  ⚠️ただしAIのエースにも等しく効くため、脚質間の相対差がどう動くかは実測が要る。
- **B-3. `slot`を強さ順にしない**——最も根本的だが、`positionTight`（後方ほど千切れやすい）と
  セットで設計されているため影響が最も広い。
- ⚠️**B-4. `solo`の`effortCost`を下げる**——これは§88〜89の禁止事項（逃げの数値を追う）に
  抵触するため**採らない**。

⚠️**原因Bを直すと「全員が集団に留まりやすくなる」＝逃げがさらに決まらなくなる可能性がある**
（§88〜89で打ち切った領域と干渉する）。修正時は必ず、逃げの成立率もbefore/afterで測ること。

# この弾で得た教訓

⚠️**「プレイヤーで測ると条件の妥当性を疑われる」場面では、AI同士の分布を見ると
留保が丸ごと消える。** 第74弾-Cは正しい観測をしていたのに「装備なし・作戦固定」という
留保のせいで「疑い」止まりだった。⚠️**同じ現象を、条件依存の無い形で測り直す方法が
無いかを先に考えるべきだった。**

⚠️**式の意図が正しくても、他の仕組みと掛け算になると壊れる。** 逃げ役の割り当て式は
単体では現実に忠実で、逃げの弱さは別途既知だった。⚠️**2つとも「既知で妥当」だったために、
その積が誰にも見えていなかった。** 今後、既に打ち切った領域（§88〜89等）がある場合は、
**そこへ選手を送り込む経路が他に無いか**を確認すること。
原因Bも同じ形で、`slot`＝強さ順（もっともらしい）と`regen`＝後方ほど回復（もっともらしい）の
**積が「強い者ほど回復できない」**になっていた。

⚠️⚠️**原因Bの機構を、このセッション中に2回間違えた**（①速く進んで単独走になる
②前方の小集団で風除けを失う）。どちらもコードを読んだ上での、もっともらしい推論だった。
**正解にたどり着いたのは、推論をやめて`src`を複製・計装し、消耗と回復を実測してからである。**
⚠️**simの因果を推論で当てようとしないこと。** 特に`solo`のように「原因でも結果でもある」
状態量が絡む場合は、**結果側の状態を除外した条件（今回は`draft`中のtickだけ）で測り直す**まで
結論を出さない。第73弾の教訓（古い観察を疑う）の、同じセッション内版だった。

## 試した候補と結果

| 候補 | 内容 | 想定脚質が最上位 | 逃げ切り率の変化 |
|---|---|---|---|
| ベースライン | — | **1/7** | 0〜28% |
| A のみ | 逃げ役の`sprintGap`依存を緩和（2箇所） | 1/7相当 | ⚠️クリテ12%→44% |
| **B-regen** | **`regen`を飽和型へ**（`0.35+0.65*min(1,b/0.25)`） | **3/7** | ⚠️丘陵28%→65% |
| B-regen＋アコーディオン | 後方に加減速消耗を新設 | 2/7 | ⚠️丘陵→75% |
| finish相性のみ | `finishAbility`に`typeAffinityBonus`を合流 | 2/7 | ほぼ不変 |
| B-regen＋finish相性 | 上記2つ | 2/7 | ⚠️丘陵→60% |

**判明したこと：**
- ⚠️**`regen`の飽和が唯一はっきり効くレバー**（1/7→3/7）。山岳ロードでCLMが×0.54→×1.52になり
  初めて最上位になった。位置モデルが主因だという診断は正しかった。
- ⚠️**アコーディオン消耗（後方ほど加減速で削られる）は、この形では効かなかった**（3/7→2/7）。
  ユーザー指摘の「後ろにいる代償」自体は現実に即しているが、⚠️**エネルギー消耗として足すだけでは
  トレードオフにならない**——後方の選手は元々余力があるので、消耗を増やしても順位が動かない。
- ⚠️**どの候補も逃げ切り率を暴走させる**（丘陵28%→60〜75%）。regenを緩めると小集団（＝逃げ）が
  生き残れるようになるため。⚠️**§88〜89で「成立しない」と打ち切った逃げが、副作用で成立しすぎる側へ
  振れる。** ここは必ずセットで見ること。

## ⚠️解析で判明した、もう1つの設計上の穴

`finish.js:68` 山頂決着＝`climb*0.75 + sprint*0.25`。実際の能力値を入れると：

- CLM（climb 86／sprint 63）＝ 64.5 + 15.75 = **80.25**
- PUN（climb 79／sprint 79）＝ 59.25 + 19.75 = **79.00**

⚠️**山頂決着でクライマーの優位はわずか+1.25しかない。** climbで+7ある差を、
sprintの0.25の重みが打ち消している。⚠️**「万能型が専門家を打ち消せる」重み付けになっており、
PUNが全登坂コースで最強になる直接の原因。** これは定数の調整ではなく決着式の設計問題。

また⚠️**`finishAbility`には`typeAffinityBonus`が入っていない**（`segmentAbility`には入っている）。
第50弾が「僅差ゴール集団ではバッジが無かったことになっていた」と同じ穴を塞いでいるが、
⚠️**脚質相性だけが取り残されている。** ただし単独では効かない（先頭集団に残れていないため）。

## ⚠️掃引を打ち切った理由

4回の候補測定で2/7〜3/7を行き来し、収束しなかった。⚠️**これは§88〜89で7回繰り返した
「機構を1つ特定→狭く直す→効かない→別の機構を特定」と同じ形である。** 8回目に入る前に
意図的に停止した。**次にやるべきは、さらに定数を探すことではない。**
