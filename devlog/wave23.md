# 第23弾：拠点マップの重なり順・導線の総点検＋散歩先拡充＋セリフ大量追加

**背景**：2026-08にユーザーから12項目の不具合・要望の一括報告。調査の結果、見た目の症状は
バラバラだが根本原因は3系統に集約されることが分かった。

- **A. 描画順（painter's sort）が「1点のy座標」しか見ていない**：大きな設置物（建物・ジム・
  チームカー・ラック）は画面上で広がりを持つのに、ソートキーはアンカー1点のy。アンカーより
  手前/奥にいる選手との前後関係が壊れる。
- **B. 屋外ルートが建物footprintと交差しても検証されていなかった**：第21弾の検証器は
  「小物との点クリアランス」「コース横断回数」だけを見ており、**建物の矩形との交差**を
  見ていなかった。前庭ベンチへのルート(w=5.1)は建物(w:5〜14)の内側を通っている。
- **C. データの表現力不足**：ベンチの「座る向き」を屋内椅子用の反転規則(`!chairFlip`)で
  流用している／木の影が汎用の自動オフセット式で幹とずれる／セリフが第21弾から未拡充。

## 2. 前面帯ルールの実装

`BaseView.jsx`のdrawOrder構築で：
```js
const FRONT_L = BASE_VIEW_CLUBHOUSE.l - BASE_VIEW_CLUBHOUSE.hl; // -4.5
const FRONT_W = BASE_VIEW_CLUBHOUSE.w + BASE_VIEW_CLUBHOUSE.hw; // 14
const inFront = (w, l) => l < FRONT_L - 0.05 || w > FRONT_W + 0.05;
sortY = inFront(item.w, item.l) ? CLUBHOUSE_SORT_Y + 1 + rawY * 1e-3 : rawY;
```
- `propItems`の各要素にw/lを持たせる（現在はsortY+nodeのみ）。選手は`act.w/act.l`。
- 変換は単調（前面帯内の相互順序はそのまま）。前面帯の要素より南に「建物の奥側」要素は
  存在し得ない（敷地はw≤16でy最大736<840.5）ので破綻しない。
- 建物の裏（w<5・l>5.5）の要素は従来どおり素のyで建物より先＝奥に描かれる。

### 追記（2026-08・ユーザー再指摘への対応）

「ベンチと座る向きが治ってないような気がします」との再指摘を受けて再調査した結果、
**向きの問題ではなく、前庭ベンチ2脚(bench-plaza0/1)とその着席者が丸ごと描画から
消えていた**（見えなくなっていた）ことが判明した。原因は§2の前面帯ルールの実装漏れ：
南（`l<frontL`）と東（`w>frontWMax`）だけを対象にしており、**西**（`w<frontWMin`）を
対象に入れ忘れていた。前庭ベンチは建物のすぐ西（w=4.2〜4.3、壁までわずか0.7）にあり、
このケースに直撃していた——建物全体の1点sortY(840.5)より低い自分のsortY(≈625)で
クラブハウスの巨大な不透明atomicグループより後(奥)に並び、完全に隠れて見えなくなって
いた。湖のほとり(stroll-pond、w=0.9)も同じ条件に当てはまり影響を受けていたはず。

**修正**：`inFrontBand`に西側の条件（`w<frontWMin`かつ建物のl奥行き範囲内に限定——
遠景の背景木まで巻き込まないため）を追加。DOM上にマーカーを直接描画して世界座標→
画面座標の変換自体を検証する手法（`document.body.appendChild`で赤い印を実際の
client座標に置く）で、修正前は該当座標に何も見えず、修正後は前庭ベンチ2脚が両方とも
正しく見えることを確認した。

**教訓**：Playwrightでの目視確認時、パン操作（ドラッグ）の計算がズレて実際には
別の場所をスクリーンショットしていたため、当初「向きが直った」と誤判定してしまった
（bench-home1は南側なので今回のバグの影響を受けておらず、たまたま正しく見えていた）。
以後、パン操作を信用せず、DOM上に直接マーカーを置いて画面座標変換そのものを
検算する手法を優先する。

**追加確認（同日）**：西側修正が他の行き先（ジム・湖のほとり）にも同じ効果を
及ぼしているかを、SVG内の実際の描画順（DOM上の兄弟要素index）を直接比較する
手法で再検証した。クラブハウス本体グループのindexに対し、ジム利用中の選手
（gym0・gym2、実測でリアルタイムに捕捉）と前庭ベンチ2脚（bench-plaza0/1）が
いずれも後続（＝手前・可視）に描画されていることをDOM上で直接確認した。
湖のほとり(stroll-pond)は選手が実際に立ち寄る瞬間をelementFromPointで捕捉し、
その画面座標の最前面要素が`<image>`（人物スプライト）であることを確認した
（クラブハウスのポリゴンではない＝隠れていない）。gym1・stroll-streamは
観測ウィンドウ内で選手の滞在を捕捉できなかったが、`inFrontBand`の判定は
座標(w,l)のみに依存する共通ロジックのため、同条件を満たす他の地点と
同一の扱いを受けることは判定式から自明。

### 訂正（2026-08・上記「西側修正」を撤回）

上記の「西側前面帯ルール追加」は**誤った修正だった**。ユーザーから直接の指摘：
「それは壁の向こう側にあるので見えないだけです。木もベンチも。」——前庭ベンチ
（w=4.2〜4.3）は建物の**西壁（back側の2面のうち1つ、`Room.jsx`が`backFacePair`で
solid描画する本物の壁）のすぐ外側**にあり、この壁は高さ(wallHeight=40)を持つ
奥壁として意図的に不透明で描画されている。ここに立つ物体が壁の陰に隠れて
見えなくなるのは、このゲームのカメラ視点（南東寄りの2:1ディメトリック）における
**正しい遮蔽**であり、バグではなかった。「見えない」ことだけを根拠に前面帯を
西側にも拡張したのは、視認性の問題と前後関係の正しさの問題を混同した誤診断。
**`inFrontBand`は南・東の2方向のみに戻した**（西側条件を削除）。ジム・湖のほとり
についても同様に、建物西壁の裏に回り込む形の可視性強制は撤回済み（該当箇所は
元々`stroll-pond`(w=0.9)のみで、ジム利用スロットはこの壁の外側条件に該当しない
ため実質的な影響はなかった）。

**教訓（重ねての反省）**：「本来見えるべきものが見えない」という思い込みは、
まず「本当に見えるべきなのか」（このカメラ角度・この壁配置で、その位置は
遮蔽されて当然ではないか）を疑ってから対処すべきだった。DOM上の描画順を
機械的に検証しても、それが「正しい遮蔽」と「バグによる誤消失」のどちらの
結果であるかまでは判定できない——判定には建物の壁配置（`Room.jsx`の
`backFacePair`/`visibleFacePair`）を実際に読んで、どの2面が不透明な奥壁として
描画されるかを確認する必要があった。

### 本当の原因（座り向きの不整合）

ユーザーの追加指摘：「向きに関しては選手の座りモデルかベンチ どちらかを
反転させるだけで治る」。前庭ベンチを一時的に画面最前面へ強制表示するデバッグ手法
（DOM上で対象ノードを`appendChild`し直すだけ・ソースは変更しない）で実際の着席
描画を直接確認したところ、`bench-plaza0/1`（データ上`flip:false`）は着席者が
座面から浮いたような不自然な位置に見えるのに対し、`bench-home0/1`
（`flip:true`）は自然に着席していた。

原因は`flip`の値そのもの：`PixelPerson`の`SIT`スプライトは頭位置を他ポーズと
揃えるための専用アンカー（`SIT_ORIGIN_COL=6`、22列中かなり左寄り）を使っており、
脚は反対側（右）に大きくはみ出す非対称な絵になっている。この非対称性は
ベンチ什器側の非対称性（`anchorCol=20`、41列中ほぼ中央）と噛み合わないため、
「什器と人物を同じ値で反転させる」という設計自体は正しくても、**どちらの
flip値でも机上で自動的に整合する保証はなく、実際にどちらが正しく収まるかは
個別に確認が要る**——今回は`true`側でのみ両者が正しく収まることが実測で
判明した。前庭ベンチのデータは元々`flip:false`だったが、これが誤りだった。

**修正**：`data/baseViewBuildings.js`の`BASE_VIEW_PROPS.benches`と
`BASE_VIEW_OUTDOOR_SPOTS`の両方で、`bench-plaza0`/`bench-plaza1`の
`flip`を`false`→`true`に変更（ホームストレートの2脚と同じ値に統一）。
`sitFlipFor()`・`BENCH_FLIP`テーブルなどロジック側は無変更——値の食い違いだけが
原因だったため、データ修正のみで解決した。

**検証**：`deviceScaleFactor:3`の高解像度スクリーンショットで、修正後の
`bench-plaza0`（強制前面化）と`bench-home1`（自然に可視）を並べて比較し、
どちらも背もたれに背を向け脚を自然に投げ出した同一の構図で着席していることを
確認。`tools/verify_baseview.mjs`も引き続きOK、`npm run build`成功。

### 再訂正・最終確定（2026-08・ユーザー指示）

上記「flip値をtrueに揃えれば整合する」という分析もユーザーから明確に否定された
（「あなたの考察は100%間違っています」「屋外にあるベンチを全て反転させなさい」）。
**最終的な正解は「什器と人物を同じ値で反転させる」設計そのものの誤りを認め、
ベンチ什器側だけを人物と逆符号で描くこと**だった。ベンチのスプライトと人物SITの
スプライトは素の向きが互いに逆手性（片方の「左向き」がもう片方の「右向き」に相当）
のため、同符号では原理的に噛み合わない。

**実装**：`Props.jsx`の`benchNode`で什器を`flip: !flip`で描画（人物側の
`sitFlipFor`＝`BENCH_FLIP`は従来どおり`flip`をそのまま使う）。データの`flip`は
「組」の向きとして4脚ともtrueのまま。高解像度スクリーンショットで、着席者の背中が
背もたれに接し座面の板の上に座る正しい構図になったことを確認した。

**同時対応：街灯の影のずれ**（ユーザー指摘）。街灯スプライトのanchorはbbox中央下
（col13/26）だが、支柱の接地部は右寄り（最下段の実測でcol18〜23・中心≈20.5）に
あり、さらに`pixelObjectNode`の影の自動配置が影を奥へ寄せるため、影が支柱の
左上に浮いて見えていた。`lampNode`に`shadowDx:3.8, shadowDy:3.4`を追加して
支柱の真下へ戻した（木の影と同型の問題。街灯3本すべてスクリーンショットで確認）。

**12項目の最終確認（同日・実測）**：DOM描画順の直接検証＋スクリーンショットで
以下を確認——入館直前の選手(9.5,-4.86)が建物グループより後（手前）に描画される／
ジム装飾はground layer（index 4、全員より奥）／ラック乗降点の選手がラック什器より
後に描画される／チームカーが建物グループより後に描画される。`pageerror`ゼロ。
`tools/verify_baseview.mjs`（壁交差ゼロ・導線クリアランス・扉経由・コース横断回数）OK。
