## 1. カメラ：選手フィーチャー機能（先頭追従／自チーム選手追従の切替）

### 1.1 現状（v10で実装済みの前提）
`RaceView`（`roadrace_v10.html:1124`〜）に、まだゴールしていない選手の広がりに自動フィットする「先頭集団追従カメラ」を実装済み（`cam`ステート、`roadrace_v10.html:1127`／カメラ計算は`tick()`内`roadrace_v10.html:1201-1214`）。現状はこの1モードのみで、特定選手を指定して追従する手段がない。

### 1.2 方針（確定：自チームの選手のみを対象）
- `camMode`ステートを追加。値は`"lead"`（既存：先頭集団追従） または `riderId`（自チーム選手のいずれかのIDを指定＝その選手のグループに追従）。
- UI：俯瞰マップ上部に自チーム選手（最大6名）を小さなチップ（ゼッケン風の丸、チーム内の色分けを流用）として横並び表示し、タップで`camMode`を切替。「先頭」チップも常設し、いつでも先頭集団追従に戻せる。
- レース中いつでも切替可能（📻無線指示と同様、`lockedRef`による最終区間ロック後も**カメラ切替自体は許可**する。結果には影響しないため制限する理由がない）。

### 1.3 カメラ計算ロジックの変更
`tick()`内のカメラ計算（`roadrace_v10.html:1201-1214`）を関数化し、`camMode`に応じて分岐：
```
if (camMode === "lead") {
  framing = unfinished.length > 0 ? unfinished : riders;  // 既存ロジックのまま
} else {
  const focus = riders.find(r => r.e.id === camMode);
  if (!focus || focus.e.finished) {
    // フィーチャー対象が既にゴール済み／無効な場合は自動的に"lead"へフォールバック
    framing = unfinished.length > 0 ? unfinished : riders;
  } else {
    // focusと同じグループ(gid)の選手だけで枠を決める＝その選手の集団内の駆け引きに寄る
    framing = riders.filter(r => r.gid === focus.gid);
  }
}
```
- 中心（`center`）・ズーム幅（`span`）の算出式自体（`(maxF-minF)*1.6`をMIN/MAX_VIEW_FRACでクランプ）はそのまま流用できる。対象がグループ内1名だけ（＝千切れて独走）の場合はspanがMIN_VIEW_FRACに張り付き、その選手単体にきれいにズームする。
- フィーチャー対象がゴールした瞬間、`"lead"`に自動で戻し、画面に小さく「📻 ◯◯選手ゴール、先頭集団に切替」のようなライブテキスト（既存の`liveRef`機構を流用）を出す。

### 1.4 実装コスト・リスク
- 低〜中。既存のカメラ計算・`gid`（グループID、`roadrace_v10.html:1194`で毎ティック計算済み）をそのまま使えるため、新規データチャネルは不要。UIチップの追加のみが新規要素。

## 2. ローテーション／トレインの視覚表現強化＋ズーム強化

### 2.1 現状の課題
実際の競馬中継（添付画像）では、集団内で「今前に出ている選手」「後方で脚を溜めている選手」「外を回って上がってくる選手」の**前後（進行方向）の位置関係**がはっきり見える。対してv10の実装（`roadrace_v10.html:1287-1289`）は、`slot`（ローテーション待ち順）によるオフセットを**横方向（俯瞰マップのY軸＝コースの左右揺れ軸）にのみ**適用しており、進行方向（X軸）は牽引中かどうかに関わらず全選手がほぼ同一座標に描画される。そのため「集団が一列になって順番に入れ替わる」動きが視覚的に表現できていない。

### 2.2 方針（確定：X軸にもローテーション位置を反映＋ズームを一段強める）
**a) 前後方向オフセットの追加**
`slot`（0＝牽引中、1,2,...＝待機順、eligible.length＝ローテーション非参加＝集団後方）を使い、描画用のX方向オフセット`rotFrac`を新設：
```
rotFrac(r) = -(r.slot / (eligible.length || 1)) * ROT_X_SPAN
```
- `ROT_X_SPAN`は集団の縦一列表現の"長さ"をfrac換算で決める定数（ズーム幅`span`に対する比率、例：現在のカメラspanの15%程度）。ズームが強いほど絶対距離としては短く、弱いほど長く見える＝ズーム連動で自然な見た目になる。
- 牽引中（slot=0）が最も前（オフセット0）、待機順が増えるほど後方にオフセットし、単騎列（paceline）らしい配置になる。
- ローテーションで牽引が交代する瞬間（`rotIdx`が進み`slot`が全員1つずつ繰り上がる、`roadrace_v10.html:737,745`）、新しい牽引者が後方から前方へ、元の牽引者が前方から後方へ**滑らかに移動する**ように、`slot`変化を即座に反映せず数ティックかけて補間する（v10の`dropOffset`が使っている遷移演出パターン＝`droppingFrac`と同様のイージングを`slot`のオフセットにも適用）。これが「順番に前に出て、また下がって外を回り込む」動きの再現になる。
- 実データ（`finishTime`）には一切影響しない、既存の「見た目専用チャネル」の方針を踏襲。

**b) ズームの強化**
- `MIN_VIEW_FRAC`（現行0.07）をさらに下げて集団密集時の拡大率を上げる（例：0.045〜0.05）。ただし、これにより追加した前後オフセット（rotFrac）が画面外にはみ出しやすくなるため、`ROT_X_SPAN`は絶対距離ではなくspan比率で決める設計（上記）にして、過度な拡大時でも列がフレーム内に収まるようにする。
- 横方向（`SLOT_LANE_SPACING`等）のオフセット量も、ズームが強くなった分だけ相対的に大きく見えるため、現行値からの微調整（縮小方向）が必要になる可能性がある→実装後にプレイテストで調整。

**c) 牽引選手の視認性向上**
- 現状も牽引中は白縁で表現済み（`roadrace_v10.html`のcircle stroke条件）。追加で、次に牽引する選手（slot=1）に薄い予告リング（例：黄色の細い破線）を付け、「もうすぐ交代する」ことを事前に示す（実際の中継で"誰が次に上がってくるか"を目で追う楽しさに相当）。

### 2.3 実装コスト・リスク
- 中。前後オフセット・イージング補間は新規ロジックだが、既存の`slot`/`dropOffset`パターンの延長線上にあるため設計難度は高くない。ズーム値の再調整はプレイテストしながらの微調整が必要（見た目のみでゲームバランスには影響しない）。

## 3. ゴール直前の拡大＋スローモーション演出

### 3.1 方針（確定：最終区間突入時に発動、既存の`lockedRef`判定を流用）
- 既存の「最終区間ロック」判定（`roadrace_v10.html:1216-1219`、いずれかの選手が`course.finalIdx`区間に入ると`lockedRef.current = true`）が発生した瞬間から、フィニッシュまでの間だけ次の2つの演出を追加で有効化する：
  1. **カメラ**：`MAX_VIEW_FRAC`ではなく、専用の`SPRINT_MIN_VIEW_FRAC`（現行`MIN_VIEW_FRAC`よりさらに小さい値、例：0.035）を上限キャップとして`span`を強制的に絞り込む。スプリント勝負の細かい着差が画面いっぱいに見えるようにする。
  2. **時間進行速度**：`clock`の進行に掛かる実効倍率を、ユーザーが選んでいる`speedRef.current`とは別に`SPRINT_SLOWDOWN = 0.4`倍程度でさらに減速する（`clock += dt * speedRef.current * (lockedRef.current ? SPRINT_SLOWDOWN : 1)`）。スキップ操作（`skipRef.current`）時は従来通り即座にフィニッシュへ飛ばして構わない（スロー演出は"観戦時のみ"の付加価値のため）。
- 発動から解除まで：フィニッシュ確定（`hud.done`）まで継続し、通常は次のレース開始時に自然にリセットされる（`cam`・`clock`ともに`useEffect`の初期化で毎回作り直されるため、特別なリセット処理は不要）。

### 3.2 実装コスト・リスク
- 低。既存の`lockedRef`フラグに条件分岐を足すだけで、新規の判定ロジックは不要。カメラ側は§2のズーム計算に上限値を差し替えるだけ、速度側は`clock`更新式に係数を1つ掛けるだけ。

## 4. FA移籍市場

### 4.1 現状
`genScouts`（`roadrace_v10.html:415`）による新人スカウトのみが選手獲得手段。既存選手（他チーム所属）を獲得する手段はない。ロースター上限は`ROSTER_MAX_BY_CLASS = [12, 14, 16]`（`roadrace_v10.html:117`）、予算は`budget`（万円単位、`roadrace_v10.html:1366`で初期値300）。

### 4.2 方針（確定：即決購入方式、v7設計書§6.3を現行データ構造に合わせて具体化）
- **市場プール**：月初（月送り処理時）に`faMarketPoolSize`（クラスに応じて4〜7名程度、`SCOUT_COUNT_BY_CLASS`と同様クラス別テーブル化）の選手を生成し、ショップタブ内に新設する「FA市場」セクションに一覧表示。
  - 生成方法は`genScouts`のロジックを流用しつつ、**新人（0年目）ではなく経験を積んだ既存選手相当**として、年齢層（例：23〜30歳）・能力値のブレ幅を新人より少し広く（一部は伸び代が乏しい代わりに即戦力の高能力、一部は伸び代重視の若手混じり）生成する`genFaPool(classIdx, seed)`を新設。
  - クラスが上がるほど、より高い`power`ベース・より広い能力レンジのプールになる（既存の`CLASSES[classIdx].scout`と同じ考え方を流用）。
- **価格モデル**：`faPrice(rider) = basePrice(overall(rider)) * ageFactor(rider.age) * classMul(classIdx)`。既存の`overall()`（上位加重式）をそのまま利用し、年齢が若いほど（伸び代を評価して）やや割高、ベテランほど割安になる係数を掛ける。
- **入れ替え**：月1回（月送り時にプール全入れ替え）。前月の未契約選手は市場から消える（「あの選手を逃した」という緊張感を出す）。
- **獲得後の扱い**：契約した瞬間`roster`に加わり、通常のスカウト選手と全く同じ扱い（練習・役割設定・レース起用が可能）。ロースター上限（`ROSTER_MAX_BY_CLASS`）に達している場合は先に既存選手の解雇/引退処理が必要（既存に解雇UIがなければ、本機能と合わせて簡易な「戦力外通告」ボタンを1つ追加する）。

### 4.3 実装コスト・リスク
- 中。新規生成関数`genFaPool`・価格関数・ショップUIへのセクション追加が主な作業。既存のロースター管理・練習・起用ロジックには手を入れない（"選手が増える経路が1つ増えるだけ"という設計のため、既存システムへの影響は小さい）。ロースター上限に達している状態での契約導線（解雇/引退操作）だけ新規UIが必要な点に注意。

## 5. スタッフ雇用

### 5.1 現状
`equip`（`frame` / `wheels` / `facility`、`roadrace_v10.html:1368`）のみがチーム強化枠。買い切り式（`EQUIP_COST`）で、月次のランニングコストという概念は選手維持費（`UPKEEP_PER_RIDER`, `roadrace_v10.html:120`）にしかない。

### 5.2 方針（確定：数値ブースト枠、v7設計書§6.4を現行データ構造に合わせて具体化）
- **スタッフ種別**（3種、`equip`と並ぶ第4のスロット群として実装）：
  | スタッフ | 効果 | 実装箇所（案） |
  |---|---|---|
  | 監督（manager） | スポンサー契約更新時の条件が良くなる（`monthly`+α or `norma`-α） | `genSponsors`呼び出し時に補正 |
  | トレーナー（trainer） | 練習効果アップ（既存`facility`の効果、`roadrace_v10.html:1463`付近の`* (1 + g.equip.facility*0.15)`と同枠に上乗せ） | 練習経験値計算式に係数追加 |
  | ドクター（doctor） | 故障発生率低下・故障からの復帰期間短縮 | 既存の故障処理（`rosterFatigueAll`等のイベント効果周辺）に係数追加 |
- **雇用/給与モデル**：`equip`の買い切りとは異なり、**月給制**（`staffSalaryModel`：レベルごとに月額固定費、`budget`から選手維持費と同じタイミングで天引き）。レベルを上げるほど効果は増すが月給も増える。
- **枠数のクラス連動**：B1＝0枠（未解禁）、A＝1枠、PRO＝3枠（`classUnlockFeatureMap`的な配列で管理）。既存の「クラスごとの上限拡張」パターン（`equipMax = 3 + g.classIdx`と同じ考え方）を踏襲。
- **UI**：ショップタブ内、チーム機材セクションの隣に「スタッフ」セクションを新設。表示・購入UIは既存の`equip`購入ボタン（`roadrace_v10.html:2048-2061`）とほぼ同じ見た目・操作感で実装できる。

### 5.3 実装コスト・リスク
- 中。月給制という「毎月引かれ続けるコスト」を新規導入する点が既存の買い切り式equipと異なる唯一の設計上の新規性。月次処理（月送り時のbudget計算箇所）に1行差し込むだけで済むため実装自体は軽いが、**バランス調整**（給与額・効果量）に最も時間がかかる想定。

## 6. 実装順（推奨）

1. **§3 ゴール直前の拡大＋スロー** — 最小の変更で体感インパクトが大きい。最優先。
2. **§1 カメラ：選手フィーチャー** — 既存の`gid`・カメラ計算を流用でき、UIチップ追加のみ。次点で着手可能。
3. **§2 ローテーション/トレインの視覚表現強化** — 前後オフセット＋イージング補間の新規実装とズーム再調整が必要なため、§1・§3より重い。プレイテストでの微調整を見込んで単独スプリントとして扱う。
4. **§5 スタッフ雇用** — equip拡張の延長線上で実装しやすい。バランス調整に時間を割けるよう早めに着手。
5. **§4 FA移籍市場** — 新規生成ロジック・価格モデル・解雇UIまで含むため今回のスコープでは最も重い。最後に着手。
