## 1. 集団ゴール時のスプリント決着（TOP多発問題の解消）

### 1.1 原因（コード調査済み）
`simulateTicks`のドラフト処理（v9: `roadrace_v9.html:736-749`）で、同一集団内の選手は牽引者と**完全に同じ移動距離**を毎ティック代入される（`dist = groupDist`）。ティック解像度が1秒単位のため、同一集団でゴールした選手は文字通り同一の整数秒で`finishTime`が確定し、`fmtGap`が0.5秒未満の差を"TOP"と表示する仕様と相まって、集団ゴール時に4〜5人が同時にTOP表示される。山岳区間で目立つのは、少人数集団に分解されやすく、かつ最後まで一体で動くため。

### 1.2 方針（確定：スプリント能力で決着）
ティックシミュレーション本体（`simulateTicks`）は変更しない。**`rankSim`実行前後の後処理**として、同一ティック（`finishTime`差 < `TICK_SEC`）でゴールした選手を「フィニッシュクラスタ」としてグルーピングし、クラスタ内だけ以下のロジックで並べ替え・微小な時間差を付与する。

```
sprintScore(en) = effSprintAbility(en) * energyFactor(en.energyAtFinish) * (1 + jitter)
  energyFactor: エネルギー残量が高いほど若干有利（垂れているとスプリントで沈む）
  jitter: ±8%程度の乱数（毎回同じ決着にならないように）
```
- クラスタ内をsprintScore降順に並べ替え、先頭を基準に`fmtGap`と同じ表示ロジックで**0.0〜3.0秒程度**の現実的な差を機械的に付与（最小刻み0.1〜0.3秒、クラスタ内の総広がりはクラスタの人数に応じて上限3秒程度でキャップし、不自然な大差にはしない）。
- 元々別グループ（千切れ・逃げ集団）だった選手同士の既存タイム差には一切手を加えない。あくまで「同ティック＝同集団ゴール」の場合のみ対象。
- 実装場所：`finishStage`／`finishRace`内、`rankSim(sim)`呼び出し直後にクラスタ処理を挟む形が最も影響範囲が小さい（ティック履歴・観戦アニメーションには影響しない、結果表示のみに反映）。

### 1.3 影響範囲
- 観戦画面（RaceView）のアニメーション自体は変更不要（実際の位置履歴は今まで通り）。ゴール後の結果集計（`finishStage`/`finishRace`/`gc_final`のランキング表示）にのみ影響。
- 既存のGC2日間ロジック（stage1Times＋stage2 times＝合計）にもこの微小オフセットがそのまま乗るため、GC総合成績でも同じ理由の「TOP大量発生」が同時に解消される。

## 2. 千切れ選手の遅れ過大バグ（v7設計メモの積み残し課題）

### 2.1 原因（コード調査済み）
`MAX_TICKS`（2500ティック＝約41.6分相当）に到達しても完走できない選手は、`remain / lastOwnDist`で残り距離を線形外挿する（`roadrace_v9.html:758-764`）。深く消耗した選手は`energyPenaltyMul`の下限0.35でペースが大きく落ちており、その低いペースのまま残り距離を割ると外挿時間が極端に膨らむ（+44分〜+67分のような非現実的な差の主因）。

### 2.2 対応方針（確定：対応する）
- `energyPenaltyMul`の下限を0.35→**0.55**に引き上げ、深いエネルギー枯渇時の失速を緩和。
- 外挿式の分母に安全下限を設定：`Math.max(lastOwnDist, BASE_TICK_DIST * 0.4)`とし、ほぼ停止に近いペースでの外挿による暴走を防ぐ。
- 上記に加えて、レース全体の「現実的な最大タイム差」のソフトキャップを設ける：優勝者タイムの**+35%**程度を上限に、それを超える場合は上限値に丸める（DNF相当として扱うのではなく、あくまで「大きく遅れてゴールした」という体裁を保つ）。
- 変更は`energyPenaltyMul`・外挿式・ランキング後処理の3箇所のみで、ティックの基本ロジックには手を入れない。

## 3. 2Dマップの本格的な駆け引き表現

### 3.1 現状
`RaceView`（`roadrace_v9.html:990-1210`付近）は色情報（白縁＝牽引中／赤丸＝アタック中）のみで、集団内の位置関係（誰が前・誰が後ろ）を可視化していない。同一集団の選手はほぼ同座標に重なって描画される。

### 3.2 方針（確定：本格的）
シミュレーション本体に「見た目専用」のデータチャネルを追加し、実際のレース結果（finishTime）には一切影響しない前提で、以下を可視化する。

**a) ローテーション順の可視化**
- `simulateTicks`のモード決定フェーズ（集団ごとに`eligible`・`puller`を計算している箇所、`roadrace_v9.html:706-726`）で、各選手の「次に牽引するまでの残り番数」を`slot`として計算し、`slotHist`に記録する。
  - 現在の牽引者：`slot = 0`
  - 次に牽引予定の選手：`slot = 1, 2, ...`（`eligible`配列内でのローテーション順）
  - 牽引ローテーションに参加しない選手（エース・脚を使い切ったサブアシスト等）：`slot = eligible.length`（集団の一番後ろ扱い）
- `RaceView`側で`slotAt(en, rt)`を`modeAt`/`groupAt`と同様に実装し、集団内の描画オフセット（進行方向に対して縦一列、horse-trackingのレーン表示に近い形）を`slot`に応じて決定する。カーブする横揺れ（`topLateral`）とは独立した「集団内の前後オフセット」を追加で加算するイメージ。

**b) 千切れかけの可視化**
- 選手のモードが`draft`→`solo`（＝実質的に千切れ確定）に切り替わった瞬間に、数ティックかけて集団内オフセットを「一番後ろ」まで滑らかに遷移させるアニメーション状態（`droppingFrac`のような0→1の遷移値）を持たせ、実際に位置(`pos`)が離れ始める前に視覚的な予兆を出す。

**c) アタックの爆発的表現**
- 実際の位置乖離（`mode === "attack"`で速度+15%）に加えて、アタック開始直後の数ティックだけ描画上のx方向オフセットを実際の位置差より誇張して表示し（例：実際の差の1.5倍を描画に反映、実データには影響しない）、視覚的なインパクトを出す。

### 3.3 実装コスト・リスク
- ユーザーが「本格的」を選択した通り、実装コストは中〜大（新しい履歴配列`slotHist`の追加、`RaceView`のレンダリング座標計算の拡張）。ただし**実際のシミュレーション結果（finishTime・順位）には一切影響しない**設計のため、既存のバランス調整・GC集計ロジックへの影響はゼロ。安全に着手できる部類の拡張。
- 実装順としては、後述のセーブ機能などより後回しでよい（プレイの根幹には関わらない見た目強化のため）。

## 4. OVR：種目別レーティングの追加表示

### 4.1 現状
`overall()`（`roadrace_v9.html:313-316`）は既に上位加重式（最高値50%＋2位30%＋残り3項目平均20%）でスペシャリストをある程度優遇している。また`AbilityGrid`コンポーネントは5つの生能力値（平坦・登坂・スプリント・スタミナ・独走）を個別のバーで既に表示済み。

### 4.2 方針（確定：計算式は現状維持、種目別レーティングを追加表示）
生の5能力値とは別に、実際のレース種別（`TEMPLATES`の`favors`／`SEG_LABEL`）に対応した**複合適性スコア**を新設し、選手カード・編成画面に表示する。

```
平坦適性   = flat*0.6 + solo*0.25 + stamina*0.15
山岳適性   = climb*0.7 + stamina*0.3
スプリント適性 = sprint*0.7 + flat*0.2 + stamina*0.1
独走適性(TT) = solo*0.7 + stamina*0.3
丘陵適性   = climb*0.4 + sprint*0.4 + stamina*0.2   （パンチャー向け複合)
```
- OVR計算式（`overall()`）自体は変更しない。
- 編成画面（lineup）では、**その回のレースの`favors`に対応する適性スコアを選手一覧に強調表示**し、「このレースにはこの選手が合っている」を数値で即座に把握できるようにする（現状は`TYPES[race.tmpl.favors].label`で「◯◯有利」という文言のみ）。
- 選手詳細（ridersタブ）では5種目適性をレーダーチャートまたは横棒グラフで表示し、スペシャリストほど特定の適性が突出する見た目になる（既存のAbilityGridと並べて配置）。

## 5. 新規「ヘルプ」タブ

### 5.1 方針（確定：新規タブ追加）
`home` / `riders` / `shop`と並ぶ第4のタブとして「ヘルプ」を追加。以下の内容を収録する。

**a) 役割解説（メリット・デメリット明文化）**
現状`ROLES`/`CHASE_MODES`オブジェクトの`desc`はボタンのtitle属性（ホバー時のみ）でしか見えない。ヘルプタブでは各役割について次の形式で一覧化する：

| 役割 | 得意な使い方 | 弱点・リスク |
|---|---|---|
| 第一アシスト | エースを最後まで牽引。信頼度が最も高い | 脚質が合わなくても最後まで牽引を続けるため、山岳・平坦特化コースでは他の役割より非効率な場合がある |
| 第二アシスト | 第一アシストを後方支援 | 脚がなくなると離脱（早期に貢献が切れるリスク） |
| 山岳アシスト | 山岳まで脚を温存し山岳区間で牽引 | 平坦区間では牽引せず消耗のみ進む（登坂力に乏しい選手が担うと逆効果） |
| 平坦アシスト | 平坦・丘陵のみ牽引、山岳では自然脱落 | 山岳ロード等では早々に戦力外になる |
| 逃げ要員 | 序盤の逃げ集団形成、ローテーションで牽引し合う | メイン集団に吸収されるリスク。エースの脚を使わず得点機会を作る役割 |

（無線指示：追走強化／静観／エース早期発射についても同様の表形式で解説）

**b) 能力値の目安（ベンチマーク表）**
選手生成式（`initRoster`/`genScouts`の`b()`関数：`power ± 11`の一様分布＋専門種目+14ボーナス、`power`はクラスごとにB1=58/A=66/PRO=74）から逆算し、クラスごとの「能力80が大まかに上位何%か」を静的な目安表として掲載する。

| クラス | 専門種目の理論上限（+14ボーナス込み） | 能力80の目安 |
|---|---|---|
| B1 (power58) | 約83 | 上位15%程度（かなりの好素材） |
| A (power66) | 約91 | 上位30%程度（主力級） |
| PRO (power74) | 約99 | 上位45%程度（平均的な主力） |

※厳密な確率分布はクラス昇格に伴い変動するため、目安として明記し「絶対値ではなくクラス相応の相対評価」であることを注記する。

**c) 難易度・スコアリングの目安**
- レースのグレード（★1/2/3＝`GRADE_MUL` 1.0/1.5/2.0）が賞金・ポイントに与える倍率を明記。
- クラス昇格に必要なポイント（B1=45pt、A=50pt、PRO=60pt）と、シーズン11レース（4月〜2月、3月はチャンピオンシップ）で消化できる回数から、「1レースあたり平均何ポイント取れば昇格ラインに届くか」の目安（例：B1なら11レースで45pt→平均4.1pt/レース＝★1レースなら6〜7位相当）を算出して掲載。

### 5.2 実装場所
- タブ切り替えは既存の`g.tab`（"home"/"riders"/"shop"）に"help"を追加するだけで、既存のタブ切り替えUIパターン（`roadrace_v9.html:1526`付近）を流用可能。低リスクな追加。

## 6. セーブ・ロード機能

### 6.1 現状
`localStorage`等への保存処理が一切なく、タブを閉じると進行が消える。PCM/ウイニングポスト/サカつく/栄冠ナインいずれも必須機能であり、ブラウザ版プレイテストの実用性に直結するため優先度が高い。

### 6.2 方針（確定：v10に含める）
- **自動保存**：月送り・レース結果確定・年度末処理など、ゲーム状態（`g`ステート全体）が確定するタイミングで`localStorage`に自動書き込み（キー例：`roadrace_v10_autosave`）。
- **手動操作**：ホーム画面に「セーブ」「ロード」「最初から」ボタンを追加。複数スロットは今回のスコープでは見送り、単一自動保存＋明示的な「ロード」確認ダイアログ程度に留める（複数スロット制は将来検討）。
- **互換性**：`initGame()`が返すオブジェクト形状とバージョンタグ（例：`saveVersion: "v10"`）をセーブデータに含め、将来のバージョンアップでの読み込み失敗時はフォールバックして新規ゲーム開始にする（保存データの片方向マイグレーションは行わない＝壊れたセーブは諦めて新規開始、の簡易方針）。

## 7. GC2日目「2D映像が表示されなかった」報告（未再現・要監視）

### 7.1 調査結果
自動ブラウザテスト（Playwright）で、1日目・2日目とも「観戦しながらスタート」を選択し、`gc.watch`フラグが2日目まで正しく引き継がれ、LIVE画面（俯瞰・側面マップ）が両日とも正常に描画されることを複数回確認した。コード上も`startStage2`が`gc.watch`をそのまま参照しており、不具合の経路が見当たらない。

### 7.2 対応方針
ユーザー側も発生時の詳細操作を記憶しておらず、再現条件が不明。v10では次の対応に留める：
- コード変更は行わない（再現できない不具合への当て推量の修正はしない）。
- 実装時にブラウザの`console.error`/`pageerror`をログに残す仕組み（簡易エラーバナー等）を追加し、次回同様の事象が起きた際に状況を記録できるようにしておく（他の改修の副産物として低コストで対応可能）。
